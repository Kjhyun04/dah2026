2. Architecture Philosophy

본 설계는 개별 공격에 맞춘 탐지기를 만드는 것이 아니라, 공통 Security Property와 실패 원인에 기반한 방어 능력(capability)을 정의하여 임무 중심의 의사결정을 지원하는 것을 목표로 한다. 실제 공격 캠페인에서 드러난 취약점은 암호 알고리즘이 아닌 신뢰 경계·라우팅·인증·키 관리 설계에서 발생하였다. 동일 APN 풀에서 UE 간 격리가 부재하고, PFCP/GTP-C 제어 평면은 인증되지 않으며, 평문 오라클·웹 API·가입자 DB가 무인증으로 노출되는 등 시스템은 다층적인 허점을 가진다. 또한 테스트베드는 C2 데이터와 GPS를 분리한 3개 네트워크 구조를 사용하지만, UPF hairpin으로 인해 UE 간 직접 도달이 가능하여 공격 표면이 확대된다.

따라서 방어 시스템은 다음과 같은 철학을 따른다:

  • Capability‑Driven. 12개의 공격을 12개의 탐지기로 대응하지 않는다. 모든 공격을 관통하는 보안 속성(인증, 인가, 무결성, 격리, 키 관리 등)을 식별하고, 이를 보장하는 다섯 가지 Defense Capability를 정의한다.
  • Evidence‑Based. 각 Capability는 관찰한 데이터를 Evidence 형태로 생성한다. Evidence는 표준화된 레코드 형태로 저장되고, 후속 신뢰 평가와 임무 평가에 사용된다.
  • Mission Context Aware. 단순히 “위협을 탐지”하는 것이 아니라, 신뢰 수준이 임무에 미치는 영향을 정량화한다. 임무 유형, 환경과 중요도에 따라 동일한 결함의 영향도가 달라지므로 Mission Context와 Mission Impact를 명시적으로 평가한다.
  • Pipeline Integration. 각 단계의 출력은 다음 단계의 입력으로 흘러가는 파이프라인 구조다. 독립적인 모듈은 존재하지 않으며, Threat Analysis → Defense Capability → Evidence Architecture → Trust Architecture → Mission Context → Mission Impact → Policy → Recovery → Mission Decision → Attack Mapping → End‑to‑End Architecture 순으로 흐른다.
  • Transparency and Non‑Abstraction. 모든 장에서 입력 데이터, 평가 모델, 판단 기준, 출력물을 구체적으로 정의한다. “신뢰를 계산한다”와 같은 추상적 표현을 사용하지 않고, 어떤 데이터에 대해 왜, 어떻게, 어떤 기준으로 판단하는지 명시한다.

6. Data Flow Overview

본 섹션에서는 주요 데이터 객체와 그 흐름을 요약한다. 데이터는 한 장에서 다른 장으로 연속적으로 전달되며, 임무 결정에 이르기까지 점점 높은 수준의 의미를 갖는다.

  • Attack & Threat Data. 테스트베드 토폴로지, 취약점 보고서 및 공격 시나리오가 Threat Analysis로 입력되어 Security Property와 Failure 리스트로 정제된다.
  • Capability Metrics. 각 Defense Capability는 자신이 담당하는 영역(통신, 신원·접근, 세션·네트워크, 명령, 임무)에 대한 원시 로그와 상태 정보를 수집한다. 예를 들어, PFCP/GTP-C 세션 로그와 UE간 hairpin 트래픽은 Session & Network Trust Capability로, 평문 오라클 및 API 호출은 Command Trust Capability로 제공된다.
  • Evidence Records. Capability가 생성한 원시 정보는 Evidence Architecture에서 표준화된다. 각 레코드는 발생 시간, 관련 객체(UE, eNB, GCS 등), 속성(예: 인증 실패), 메트릭 값, 심각도 등을 포함한다. Evidence Repository는 이러한 레코드를 지속적으로 축적하고 시간순으로 정렬한다.
  • Trust Vector. Trust Architecture는 Evidence 레코드를 평가 모델에 넣어 각 Capability 영역별 신뢰 점수를 생성한다. 신뢰 벡터에는 통신·신원·세션·명령·임무의 신뢰 수준(높음/중간/낮음)이 포함된다.
  • Mission Context Object. Mission Context는 신뢰 벡터와 임무 계획(임무 유형, 중요도, 환경 조건)을 결합하여 각 영역의 가중치를 설정한다. 예를 들어, 정찰 임무에서는 명령 신뢰보다 통신 신뢰가 더 중요할 수 있다.
  • Impact Assessment. Mission Impact 단계에서는 신뢰 벡터와 컨텍스트 가중치를 사용하여 각 영역의 영향 점수를 계산하고 위험 등급을 할당한다. 결과는 Policy에서 사용할 수 있는 정량적 위험 프로필로 전달된다.
  • Policy Recommendation. Policy 단계는 임무 영향 및 조직 정책에 따라 가능한 행동 옵션(계속, 제한, 감시 강화, 임무 중단)을 평가한다. 선택된 정책과 그 근거가 Recovery 단계로 전달된다.
  • Recovery Options. Recovery 단계에서는 정책에 따라 시스템을 복구할 수 있는 구체적인 후보(재인증, 세션 재설정, 대체 링크로 전환 등)를 평가하고 실행 가능성이 높은 방안을 선택한다.
  • Mission Decision. 최종적으로 Mission Decision 단계에서 정책과 복구안을 종합하여 임무 수행 여부, 조건부 수행(부분 임무), 또는 중단을 결정한다. 결정과 근거가 기록된다.
  • Attack Mapping & End‑to‑End. 임무 결정 이후 각 공격 시나리오가 어느 Capability와 Evidence에 의해 탐지되고 완화될 수 있는지 평가하며, 전체 방어 체계를 명확하게 이해한다.

7. Document Writing Roadmap

Blueprint 이후의 상세 설계 문서 작성 계획이다. 각 단계는 이전 단계의 결과를 기반으로 상세 스펙, 평가 모델, 임계값 등을 정의한다.

  1. Threat Analysis Details. 공격 시나리오와 취약점 보고서를 세부적으로 분석하여 Security Property 카테고리를 정의하고, 실패 사례를 체계적으로 도출한다. 이를 위해 표적 포트, 네트워크 토폴로지, 인증 메커니즘 등 구체적인 데이터를 재검토한다.
  2. Capability Specification. 다섯 가지 Defense Capability에 대한 상세 설계를 작성한다. 각 Capability의 입력 데이터 소스, 관찰 메트릭, 평가 모델, 출력 Evidence 구조를 정의하며, testbed에서 수집 가능한 로그를 기반으로 한다.
  3. Evidence Schema & Repository. Evidence Architecture의 데이터 모델을 설계한다. Evidence 레코드의 필드, 인덱싱 전략, 타임스탬프 처리, 저장소 구조(예: 데이터베이스 또는 파일 시스템)를 정의한다.
  4. Trust Evaluation Model. 신뢰 평가 모델을 수학적으로 정의한다. 각 Evidence가 신뢰 점수에 어떻게 기여하는지(가중치, 누적 방식), 임계값과 신뢰 등급 구간을 설정한다.
  5. Mission Context Definition. 임무 유형별 가중치 매핑, 환경 파라미터 및 중요도 척도를 정의한다. UAV 임무(정찰, 항로 지정, 물자 운송 등)에 따라 가중치가 어떻게 달라지는지 명확하게 규정한다.
  6. Mission Impact Calculation. 임무 영향 계산식을 설계한다. 신뢰 벡터와 컨텍스트 가중치를 결합하여 영향 점수를 생성하는 수식을 정의하고, 위험 등급(예: 녹색/황색/적색)을 결정하는 기준을 마련한다.
  7. Policy Rules. 조직의 방어 정책을 분석하여 Mission Impact에 따른 행동 옵션을 체계화한다. 정책 규칙, 조건, 예외를 정의하고 예시 시나리오를 검토한다.
  8. Recovery Logic. 복구 단계에서 고려할 수 있는 구체적인 절차와 알고리즘을 설계한다. 예를 들어, 세션 재설정, 재인증, 대체 통신 경로 설정 등의 세부 절차를 문서화한다.
  9. Mission Decision Logic. 정책과 복구 정보를 통합하여 최종 임무 결정을 생성하는 로직을 설계한다. 결정 근거를 기록하는 메커니즘과 Auditing 요구사항을 포함한다.
  10. Attack Mapping Matrix. 각 공격 시나리오와 Capability의 대응 관계를 표 형태로 정리한다. 탐지할 Evidence, 관련 신뢰 영역, 예상 정책·복구 선택을 표기한다.
  11. End‑to‑End Architecture. 최종 문서에서 모든 설계 요소를 종합한 시스템 아키텍처를 작성하고, 데이터 흐름·모듈 상호작용을 상세하게 기술한다.
본 Blueprint는 하드코딩된 탐지기를 설계하는 것이 아니라, 데이터와 임무 맥락에 기반하여 스스로 판단할 수 있는 방어 체계를 설계하기 위한 기초 문서이다. 취약점은 암호나 프로토콜 내부가 아닌 신뢰 경계, 격리, 인증, 키 관리의 실패에서 발생한다는 사실을 명심해야 한다. 이후 단계에서는 각 장을 상세히 설계하고, 평가 모델 및 임계값을 정의하여 자동 방어 모듈이 구현될 수 있도록 한다.
