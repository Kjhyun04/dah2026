Mission‑Centric Defense Architecture Skeleton

LTE/5G 기반 UAV C2 환경을 위한 임무 중심 방어 아키텍처 Skeleton 설계 (2026‑07‑04)
프로젝트 Mission‑Centric Defense Architecture 환경 4G/5G UAV C2 Testbed 버전 Skeleton Stage 철학 Capability‑Driven, Mission‑Aware

1. Skeleton Overview

본 Skeleton 문서는 Mission‑Centric Defense Architecture 디자인 문서의 내부 구조를 설계한다. 각 장은 목적과 범위를 명확히 정의하고, 테스트베드에서 수집 가능한 데이터와 공격 시나리오에서 도출된 위협만을 입력으로 사용한다. Skeleton은 추상적인 표현 없이 데이터 객체, 내부 흐름, 인터페이스, 표/다이어그램 요구사항을 규정하며, 이후 단계에서 이 구조를 기반으로 본문을 작성할 수 있도록 한다.

2. Chapter Skeletons

각 Chapter는 아래 항목을 모두 포함한다. Chapter Summary는 장의 역할을 요약하고, Section Tree는 구체적인 하위 섹션 구조를 보여준다. Internal Components와 Internal Flow는 데이터를 어떻게 처리하는지 설명하며, Input/Generated/Output Objects와 Interfaces는 데이터 객체와 연결 지점을 정의한다. Required Tables와 Required Diagrams는 본문 작성 시 제공해야 할 시각적 자료를 식별한다. Failure Handling은 데이터 부재나 예외 상황에 대응하는 설계 전략을 기술하고, Cross References는 다른 장과의 의존 관계를 나타낸다. Design Notes는 설계 시 고려해야 할 현실적 제약과 판단 기준을 기록한다.

Threat Analysis

Chapter Summary

테스트베드 인프라와 공격 시나리오를 분석하여 공통 Security Property와 실패 원인을 도출하고, 이를 기반으로 후속 Capability 설계의 입력을 생성한다. 개별 공격에 집중하지 않고 취약점의 근본 원인을 식별한다.

Purpose

공격 표면과 취약점을 체계적으로 분석하여 보호해야 할 보안 속성과 실패 유형을 정의하고, 각 노출면을 해당 속성에 매핑한다.

Scope

  • 대상: 테스트베드 인프라 구성 및 공격 시나리오(가용한 데이터에 한함).
  • 행위: 신뢰 경계·라우팅·인증·키 관리 등 공통 영역을 분석.
  • 제외: 암호 알고리즘 내부, PoC 코드 세부 동작.

Section Tree

  • Threat Sources – 테스트베드 노출면(H1–H8)과 공격 시나리오를 정리하고 분류한다.
  • Security Property Derivation – 인증, 인가, 무결성, 격리, 키 관리 등 보호해야 할 속성을 도출한다.
  • Failure Classification – 각 노출면을 공통 실패 유형(CWE)으로 분류한다.
  • Exposure Mapping – 노출면과 보안 속성·실패 간 매핑을 작성한다.

각 섹션은 Purpose → Input → Internal Processing → Generated Data → Output → Design Considerations 구조를 따른다.

Internal Components

  • Attack Data Ingestor – 공격 시나리오와 인프라 노출 정보를 수집한다.
  • Property Extractor – 데이터에서 공통 보안 속성을 추출한다.
  • Failure Mapper – 각 노출면을 실패 유형으로 분류한다.
  • Exposure Repository – 노출면과 속성 매핑을 저장한다.

Internal Flow

  1. Collect Inputs: 테스트베드 노출면(H1–H8), 공격 시나리오 로그와 판정 결과를 수집한다.
  2. Derive Properties: 노출 데이터에서 인증, 인가, 무결성, 격리, 키 관리 등 공통 보안 속성을 도출한다.
  3. Classify Failures: 노출면을 결함 유형으로 분류한다(CWE 기준).
  4. Map Exposures: 각 노출면을 도출된 속성과 실패 유형에 매핑하고 Exposure Map을 생성한다.

Input Objects

  • Testbed Exposure Records: H1–H8 항목(예: SITL 시리얼 포트, NAS 암호 설정, MongoDB 노출, 웹 API, 키 배포, UE 격리 부재, PFCP 노출, GPS 입력)【208159606947672†L279-L293】.
  • Attack Scenario Logs: TM1/V2 오라클 주입, TM2 PFCP 세션 삭제, NF-3 가입자 DB 탈취, NF-4 웹 무인증, NF-6 서명키 노출 등 공격 과정·관측·판정 데이터【574666281232364†L162-L176】【574666281232364†L270-L289】.
  • Kill Chain Analysis: VULN-01~VULN-06 결과와 근본원인(CWE) 분석【574666281232364†L162-L176】【574666281232364†L270-L289】.

Generated Objects

  • Security Property List: 보호해야 할 보안 속성(인증, 인가, 무결성, 격리, 키 관리 등).
  • Failure List: 공통 실패 유형(CWE-306/862 등)과 간략 설명.
  • Exposure Map: 노출면과 보안 속성 및 실패 유형 간 매핑 표.

Output Objects

  • Security Property List → Defense Capability 장.
  • Failure List → Defense Capability 장.
  • Exposure Map → Defense Capability 장.

Interfaces

  • Data Import Interface: 테스트베드와 공격 시나리오 로그를 불러오는 파일/DB 연결.
  • Exposure API: 후속 Capability 설계에서 노출면 정보를 조회하는 인터페이스.

Required Tables

  • Security Property vs Failure Table – 각 보안 속성에 대해 관련 실패(CWE)를 요약.
  • Exposure Map – 노출면, 속성, 실패, 증거를 4열로 나열.

Required Diagrams

  • Threat Analysis Flow – 위 내부 흐름 4단계를 시각화.
  • Kill Chain Mapping – 공격 시나리오를 Cyber Kill Chain 단계에 배치하고 보안 속성과 연결.

Failure Handling

  • 테스트베드에서 수집할 수 없는 데이터가 있을 경우 해당 노출면을 제외하거나 보완 수단을 명시한다.
  • 공격 로그가 불완전하거나 오류가 있는 경우 검증된 증거만 사용한다.

Cross References

  • Defense Capability – 보안 속성과 실패 유형을 Capability 정의에 전달한다.
  • Attack Mapping – 각 노출면과 공격 시나리오를 매핑한다.

Design Notes

  • 공격별 탐지기가 아닌 공통 속성에 기반한 설계를 위해 보안 속성을 일반화한다.
  • 테스트베드에서 측정 가능한 데이터만 사용하며, 실제 수집 불가능한 가상의 센서는 포함하지 않는다.
  • 보안 속성과 실패 유형의 정의는 가능한 한 표준(CWE, ATT&CK) 분류 체계를 따르며, 이후 단계에서 확장 가능하도록 한다.

Defense Capability

Chapter Summary

Threat Analysis에서 도출한 보안 속성과 실패 유형을 기반으로 다섯 가지 Defense Capability를 정의한다. 각 Capability는 책임 영역을 명확히 하고, 테스트베드에서 수집할 수 있는 메트릭을 지정한다.

Purpose

인증·인가·무결성·격리·키 관리 등의 속성을 보장하는 능력을 정의하고, 각 능력이 관찰해야 할 원시 데이터를 명시한다.

Scope

  • 5개의 Capability만 정의하며, 공격별 감지기를 생성하지 않는다.
  • 각 Capability는 자신의 책임 영역(통신, 신원·접근, 세션·네트워크, 명령, 임무)에 해당하는 데이터만 수집한다.
  • 평가 모델과 임계값은 다음 단계에서 설계한다.

Section Tree

  • Capability Overview – 공통 역할과 철학을 설명한다.
  • Communication Trust Capability – 통신 채널(ARIA 암호, NAS, PFCP/GTP)의 무결성·신뢰성 모니터링.
  • Identity & Access Trust Capability – USIM 인증, 가입자 DB 접근, API 인증 등 신원·권한 검증.
  • Session & Network Trust Capability – UE 격리, PFCP 세션 상태, hairpin 트래픽 감시.
  • Command Trust Capability – MAVLink 명령 소스 검증, 오라클 주입 탐지, 웹 명령 인증.
  • Mission Trust Capability – 임무 계획과 관련된 시스템 상태, 키 분배 상태, GPS 입력의 신뢰성 감시.

각 Capability 섹션은 Purpose → Input → Internal Processing → Generated Data → Output → Design Considerations 구조를 따른다.

Internal Components

  • Metric Collector – 각 Capability에 필요한 원시 로그와 상태 정보를 수집한다.
  • Metric Preprocessor – 수집된 데이터를 정규화하고 필터링한다.
  • Capability Monitor – 정의된 보안 속성에 따라 메트릭을 해석하고 원시 Evidence 이벤트를 생성한다.

Internal Flow

  1. Receive Definitions: 보안 속성, 실패 리스트를 입력받아 Capability별 책임을 할당한다.
  2. Identify Metrics: 테스트베드 로그에서 관찰 가능한 메트릭을 매핑한다. communication: ARIA 암호 상태, NAS 암호 우선순위, PFCP/GTP 세션 로그, GPS 입력【208159606947672†L260-L293】; identity & access: USIM 인증 로그, MongoDB 접속 로그, web API 인증 로그【208159606947672†L279-L289】【574666281232364†L270-L289】; session & network: PFCP session deletion, UE hairpin traffic, S1-U/GTP-U integrity【208159606947672†L279-L293】【574666281232364†L304-L344】; command: MAVLink command source logs, Oracle injection attempts, web cmd calls【488147192654095†L50-L57】【574666281232364†L162-L176】; mission: mission plan parameters, key distribution state, GPS input integrity【208159606947672†L279-L293】.
  3. Collect Metrics: Metric Collector가 각 영역의 로그를 수집한다.
  4. Generate Raw Evidence: Capability Monitor가 사건을 감지하여 Evidence Architecture로 전달한다.

Input Objects

  • Security Property List – Threat Analysis에서 전달된 보호 속성.
  • Failure List – Threat Analysis에서 전달된 실패 유형.
  • Exposure Map – 각 노출면과 매핑된 속성.
  • Testbed Logs – 시스템 로그, PFCP/GTP 세션 상태, MAVLink command logs, API access logs.

Generated Objects

  • Capability Definitions: 5개 Capability 각각의 역할과 책임 영역 문서화.
  • Monitored Metrics: 각 Capability가 수집해야 할 메트릭 목록.
  • Raw Evidence Events: 메트릭을 기반으로 발생하는 원시 Evidence 이벤트.

Output Objects

  • Capability Definitions → Evidence Architecture.
  • Monitored Metrics → Evidence Architecture.
  • Raw Evidence Events → Evidence Architecture.

Interfaces

  • Metric Ingest Interface: 로그 및 데이터 스트림을 Capability 모듈로 전송하는 메커니즘.
  • Evidence Emitter: 원시 이벤트를 Evidence Architecture로 전달하는 비동기 큐 또는 API.

Required Tables

  • Capability vs Metrics Table – 각 Capability와 관련된 입력 메트릭을 요약.
  • Capability vs Exposures Table – 노출면이 어느 Capability에 의해 모니터링되는지 표시.

Required Diagrams

  • Capability Flow Diagram – 각 Capability가 데이터를 수집하고 Evidence를 생성하는 흐름을 표시.
  • Capability Responsibility Map – 보안 속성과 Capability 간 매핑을 시각화.

Failure Handling

  • 로그 누락 또는 센서 오류 발생 시, Capability는 해당 메트릭의 상태를 “불확실”로 표시하고 Evidence Architecture에 보고한다.
  • 정상 임무 절차로 간주되는 활동과 공격 징후를 구분하기 위한 기준선 학습이 필요하며, 초기 스켈레톤에서는 그 필요성을 명시한다.

Cross References

  • Evidence Architecture – Capability에서 생성된 Evidence를 전달한다.
  • Attack Mapping – 각 Capability가 어느 공격을 탐지할 수 있는지 매핑한다.

Design Notes

  • 각 Capability는 독립된 감지기가 아니라, 공통 보안 속성을 모니터링하는 모듈이다.
  • 테스트베드에서 실제로 수집 가능한 로그(예: PFCP 로그, MongoDB 접근 로그, MAVLink 명령 로그)만 사용한다.
  • Capability별 평가 모델은 다음 단계에서 정의하며, Skeleton에서는 입력과 출력 구조만 설계한다.

Evidence Architecture

Chapter Summary

Capability 모듈이 생성한 원시 Evidence 이벤트를 수집·정규화·연관 분석하여 표준화된 Evidence 레코드로 변환하고, 이를 저장소에 축적한다.

Purpose

다양한 Capability에서 발생하는 이벤트를 공통 스키마로 통합하여 후속 신뢰 평가가 가능한 Evidence Repository를 구축한다.

Scope

  • 수집: Capability가 전송한 모든 원시 Evidence를 수신한다.
  • 정규화: 이벤트 필드를 표준화하고 시계열로 정렬한다.
  • 연관 분석: 관련 이벤트를 상호 연관지어 의미 있는 레코드로 만든다.
  • 제외: 신뢰 평가 모델의 계산식(Trust Architecture에 위임).

Section Tree

  • Evidence Sources – Capability에서 전달되는 이벤트 스트림을 설명한다.
  • Collection and Normalization – 데이터 형식 통일, 타임스탬프 동기화.
  • Correlation Engine – 서로 다른 Capability 이벤트를 상호 연관 분석한다.
  • Evidence Repository – Evidence 레코드를 저장하고 검색하는 저장소 설계.

모든 섹션은 동일한 구조(Purpose → Input → Processing → Generated Data → Output → Design Considerations)를 따른다.

Internal Components

  • Evidence Collector – 원시 Evidence 이벤트를 구독하여 수신한다.
  • Normalizer – 이벤트 속성 이름과 형식을 표준화한다.
  • Correlation Engine – 시간과 엔티티 기준으로 관련 이벤트를 연결한다.
  • Evidence Repository – 정규화된 Evidence 레코드를 저장한다.

Internal Flow

  1. Receive Events: Evidence Collector가 Capability에서 발생한 원시 이벤트를 수신한다.
  2. Normalize Fields: Normalizer가 이벤트 필드를 표준 스키마(발생 시간, 주체, 속성, 메트릭, 심각도 등)로 변환한다.
  3. Correlate Events: Correlation Engine이 동일 엔티티·시간 윈도우 내 이벤트를 연결하여 복합 사건을 형성한다.
  4. Store Evidence: Evidence Repository에 정규화된 레코드를 저장하고 인덱싱한다.

Input Objects

  • Raw Evidence Events – Capability에서 전송된 이벤트 스트림.
  • Evidence Schema Definition – 표준 필드 정의(예: 시간, 엔티티, 속성, 메트릭, 심각도).

Generated Objects

  • Normalized Evidence Record – 표준 스키마로 변환된 Evidence.
  • Evidence Repository Index – 시간/엔티티 기반 인덱스.
  • Correlation Linkage – 관련 이벤트 간 관계 정보.

Output Objects

  • Evidence Records → Trust Architecture.

Interfaces

  • Evidence Ingest API: Capability 모듈이 이벤트를 게시하는 인터페이스.
  • Evidence Query API: Trust Architecture가 Evidence를 조회하는 인터페이스.

Required Tables

  • Evidence Schema Table – 필드 이름, 타입, 설명을 요약한다.
  • Correlation Mapping Table – 이벤트 유형 간 연관 규칙을 정리한다.

Required Diagrams

  • Evidence Flow – 수집→정규화→연관→저장 흐름을 도식화.
  • Repository Architecture – Evidence 저장소 구조(테이블·인덱스 등)를 나타낸다.

Failure Handling

  • 이벤트 데이터가 손상되거나 필드가 누락된 경우, 해당 이벤트를 무효로 처리하고 별도 오류 레코드를 생성한다.
  • 수신 버퍼 초과 등 시스템 자원 고갈 상황에 대비해 백프레셔(backpressure) 메커니즘을 설계한다.

Cross References

  • Trust Architecture – Evidence 평가를 위해 정규화된 레코드를 제공한다.
  • Attack Mapping – 어떤 Evidence가 어떤 공격 탐지에 사용되는지 기록한다.

Design Notes

  • Evidence 스키마는 향후 모델 확장을 고려하여 유연하게 설계한다.
  • 저장소는 시간·엔티티 기반 쿼리에 최적화된 인덱스를 제공해야 한다.
  • 테스트베드 환경의 트래픽 양을 고려하여 성능 요구사항을 설정한다.

Trust Architecture

Chapter Summary

Evidence 레코드를 평가하여 통신, 신원·접근, 세션·네트워크, 명령, 임무 영역별 신뢰 수준을 계산하고 신뢰 벡터를 생성한다.

Purpose

정규화된 Evidence를 토대로 영역별 신뢰 점수를 산출하여 시스템의 현재 건강 상태를 정량화한다.

Scope

  • Evidence 평가 모델과 신뢰 계산 논리를 정의한다(모델 수식은 다음 단계에서 설계).
  • 각 영역별 신뢰 점수 범주(높음/중간/낮음)를 정의한다.
  • 신뢰 벡터를 Mission Context에 전달할 수 있도록 형식을 규정한다.

Section Tree

  • Trust Evaluation Models – 영역별 평가 모델 개요를 정의한다.
  • Trust Vector Generation – 개별 점수를 종합하여 신뢰 벡터를 생성한다.

각 섹션은 Purpose → Input → Processing → Generated Data → Output → Design Considerations 구조를 따른다.

Internal Components

  • Evidence Evaluator – 정의된 모델에 따라 Evidence를 점수화한다.
  • Score Aggregator – 영역별 점수를 종합하여 신뢰 벡터를 형성한다.

Internal Flow

  1. Retrieve Evidence: Evidence Architecture에서 정규화된 레코드를 가져온다.
  2. Evaluate Scores: Evidence Evaluator가 영역별 신뢰 점수를 계산한다. 예: 통신 신뢰는 PFCP 세션 상태와 NAS 암호 설정에 기반【208159606947672†L260-L293】; 신원·접근 신뢰는 USIM 인증 로그와 MongoDB 접근 정책에 기반【208159606947672†L279-L289】【574666281232364†L270-L289】; 세션·네트워크 신뢰는 UE 격리 여부와 PFCP 삭제 이벤트에 기반【208159606947672†L279-L293】【574666281232364†L304-L344】; 명령 신뢰는 오라클 주입, 서명 검증 실패, 서명키 유출 증거에 기반【488147192654095†L50-L57】【574666281232364†L162-L176】; 임무 신뢰는 GPS 입력 무결성과 키 배포 상태에 기반【208159606947672†L279-L293】.
  3. Aggregate Vector: Score Aggregator가 영역별 점수를 조합하여 신뢰 벡터를 생성한다.

Input Objects

  • Evidence Records – 정규화된 Evidence 리스트.
  • Trust Evaluation Parameters – 각 영역별 평가 모델에 필요한 가중치·임계값(다음 단계에서 정의).

Generated Objects

  • Domain Trust Scores – 영역별 신뢰 점수.
  • Trust Vector – 전체 시스템의 신뢰 벡터.
  • Evaluation Summary – 각 점수의 근거 요약.

Output Objects

  • Trust Vector → Mission Context.
  • Evaluation Summary → Mission Context.

Interfaces

  • Evidence Query API: Evidence Architecture로부터 레코드를 조회하는 인터페이스.
  • Trust Export API: Mission Context가 신뢰 벡터를 가져가는 인터페이스.

Required Tables

  • Trust Evaluation Criteria – 각 영역별 평가 항목과 중요도를 요약.
  • Trust Vector Format – 벡터 구조와 값 범주를 기술.

Required Diagrams

  • Trust Flow Diagram – Evidence→평가→점수→벡터 생성 과정을 도식화.
  • Trust Vector Heatmap – 임무 Impact 단계에서 사용할 수 있도록 각 영역의 신뢰 수준을 시각화(다음 단계).

Failure Handling

  • Evidence 부족으로 평가 불가능한 경우 해당 영역의 신뢰를 “미정”으로 표시하고 Mission Context에 통보한다.
  • 평가 모델의 오류나 구성 실패 시 기본값과 알림 메커니즘을 설계한다.

Cross References

  • Mission Context – 신뢰 벡터를 입력받아 임무 가중치를 설정한다.
  • Policy – 신뢰 수준이 낮은 영역을 정책 규칙의 조건으로 사용할 수 있다.

Design Notes

  • 신뢰 평가 모델은 선형 또는 비선형 가중 합 방식 등 다양하며, Skeleton에서는 모델 입력과 출력 구조만 정의한다.
  • 신뢰 점수의 범주 정의(예: High/Medium/Low)는 임무 컨텍스트와 연계될 수 있도록 명확히 구분한다.

Mission Context

Chapter Summary

신뢰 벡터와 임무 계획(임무 유형, 환경, 중요도)을 결합하여 각 영역별 가중치를 설정한다. 임무 컨텍스트는 Impact 평가와 정책 결정에 영향을 미친다.

Purpose

임무의 특성에 따라 신뢰 수준이 임무 성과에 미치는 영향을 조정하기 위해 컨텍스트 가중치를 정의한다.

Scope

  • 임무 유형: 정찰, 항로 지정, 물자 운송 등 UAV 임무 범주를 정의한다.
  • 환경 조건: 날씨, 지형, 위협 수준 등 임무 수행 환경의 파라미터.
  • 중요도: 임무 실패 시 조직이 감수해야 하는 손실 수준.
  • 제외: 임무 계획 자체의 생성(운영 계획서에 포함).

Section Tree

  • Mission Parameters – 임무 유형, 환경, 중요도 등의 입력 파라미터를 정의한다.
  • Contextual Weighting – 각 신뢰 영역에 대한 가중치를 설정하는 방법을 설계한다.

각 섹션은 동일한 구조(Purpose → Input → Processing → Generated Data → Output → Design Considerations)를 따른다.

Internal Components

  • Mission Parameter Extractor – 임무 계획에서 유형·환경·중요도 파라미터를 추출한다.
  • Weighting Engine – 신뢰 영역별 가중치를 계산한다.

Internal Flow

  1. Receive Trust Vector: Trust Architecture로부터 신뢰 벡터를 입력받는다.
  2. Extract Mission Parameters: Mission Parameter Extractor가 임무 유형, 환경, 중요도를 가져온다.
  3. Compute Weights: Weighting Engine이 임무 파라미터를 기반으로 각 영역의 중요도를 결정한다.
  4. Create Context Object: 계산된 가중치와 신뢰 벡터를 결합하여 Mission Context Object를 생성한다.

Input Objects

  • Trust Vector – 영역별 신뢰 점수.
  • Mission Plan – 임무 유형, 환경 조건, 중요도를 담은 계획 문서.
  • Mission Parameter Definitions – 각 파라미터의 범위와 단위 정의.

Generated Objects

  • Contextual Weights – 각 신뢰 영역의 가중치.
  • Mission Context Object – 신뢰 벡터와 가중치가 결합된 객체.

Output Objects

  • Mission Context Object → Mission Impact.

Interfaces

  • Mission Plan Input: 임무 계획 파일/데이터베이스에서 파라미터를 읽어오는 인터페이스.
  • Context Export API: Mission Impact 단계가 컨텍스트 객체를 조회하는 인터페이스.

Required Tables

  • Mission Types Table – 임무 유형과 각 영역의 기본 가중치.
  • Environmental Factors Table – 환경 파라미터와 영향도.

Required Diagrams

  • Mission Context Flow – 신뢰 벡터와 임무 파라미터의 결합 과정을 도식화.
  • Weighting Matrix – 각 임무 유형별 영역 가중치를 표현한 행렬.

Failure Handling

  • 임무 계획 데이터가 부족하거나 파라미터가 정의되지 않은 경우 기본 가중치를 적용한다.
  • 신뢰 벡터와 가중치 간 모순이 발견될 경우 관리자에게 알리고 Impact 계산을 보수적으로 처리한다.

Cross References

  • Mission Impact – 컨텍스트 가중치를 사용하여 영향 점수를 계산한다.
  • Policy – 임무 유형 및 중요도가 정책 선택에 영향을 준다.

Design Notes

  • 임무 유형과 환경 파라미터는 조직별로 맞춤화할 수 있으므로 Skeleton에서는 구조만 정의하고 값은 추후 설정한다.
  • 컨텍스트 가중치는 합이 1이 되도록 정규화하여 각 영역의 상대적 중요도를 나타낸다.

Mission Impact

Chapter Summary

신뢰 벡터와 임무 컨텍스트 가중치를 결합하여 각 영역의 영향 점수를 계산하고 위험 등급을 도출한다. 결과는 정책 판단의 기초가 된다.

Purpose

신뢰 결핍이 임무 목표에 미치는 영향을 정량화하여 정책과 복구 판단의 근거로 제공한다.

Scope

  • 영향 점수 계산 로직과 위험 등급 구분(예: 녹색/황색/적색)을 정의한다.
  • 각 영역별 영향 점수를 종합하여 임무 전체 위험 프로필을 생성한다.
  • 제외: 정책 자체의 선택 로직(Policy 단계에 위임).

Section Tree

  • Impact Metrics – 영향 점수 계산에 사용되는 공식과 입력 변수를 정의한다.
  • Impact Evaluation Structure – 계산된 점수를 위험 등급으로 매핑한다.

모든 섹션은 Purpose → Input → Processing → Generated Data → Output → Design Considerations 구조를 따른다.

Internal Components

  • Impact Calculator – 신뢰 벡터와 컨텍스트 가중치를 입력으로 영향 점수를 계산한다.
  • Risk Categorizer – 점수를 위험 등급으로 변환한다.

Internal Flow

  1. Receive Inputs: Mission Context Object와 신뢰 벡터를 가져온다.
  2. Compute Impact Scores: Impact Calculator가 각 영역별로 신뢰×가중치 계산을 수행하여 영향 점수를 산출한다.
  3. Assign Risk Categories: Risk Categorizer가 영향 점수를 사전 정의된 등급(예: Green/Yellow/Red)으로 변환한다.
  4. Create Impact Record: 영역별 영향 점수와 등급을 포함하는 Impact Assessment Record를 생성한다.

Input Objects

  • Mission Context Object – 신뢰 벡터와 영역별 가중치를 포함한다.
  • Trust Vector – 영역별 신뢰 점수.
  • Impact Thresholds – 위험 등급을 결정하는 임계값(다음 단계에서 정의).

Generated Objects

  • Impact Scores – 각 영역별 영향 점수.
  • Risk Categories – 등급(Green/Yellow/Red 등).
  • Impact Assessment Record – 종합적인 임무 영향 기록.

Output Objects

  • Impact Assessment Record → Policy.

Interfaces

  • Impact Export API: Policy 단계가 영향 기록을 조회하는 인터페이스.

Required Tables

  • Impact Score Table – 영역별 신뢰, 가중치, 영향 점수, 위험 등급을 요약.

Required Diagrams

  • Impact Calculation Diagram – 입력→점수→등급 흐름을 도식화.

Failure Handling

  • 필수 입력(신뢰 벡터 또는 컨텍스트)가 없을 경우 임무 영향 평가를 수행하지 않고 보수적(최악) 위험 등급을 할당한다.
  • 임계값이 정의되지 않은 영역은 조직 정책에 따라 기본 등급을 적용한다.

Cross References

  • Policy – 위험 등급에 따라 정책 규칙을 선택한다.
  • Recovery – 영향 점수를 고려하여 복구 후보를 평가한다.

Design Notes

  • 영향 계산식은 곱셈/가중합 등 단순 연산으로 설계하여 실시간 평가가 가능하도록 한다.
  • 위험 등급 분포는 조직의 위험 허용도에 따라 조정 가능하도록 파라미터화한다.

Policy

Chapter Summary

Mission Impact에서 도출한 위험 등급과 조직의 정책 규칙을 기반으로 가능한 행동 옵션을 평가하고 권장 정책을 선택한다.

Purpose

조직의 안전·임무 지속성 목표를 고려하여 임무를 계속, 제한, 감시 강화, 또는 중단할지 결정하는 고수준 정책을 제안한다.

Scope

  • 정책 규칙과 조건, 예외를 정의한다.
  • 위험 등급과 임무 유형에 따른 행동 옵션을 평가한다.
  • 제외: 개별 복구 절차(Recovery 단계에서 처리).

Section Tree

  • Policy Rules Definition – 조직의 방어 정책과 규칙을 체계화한다.
  • Action Evaluation – 위험 등급과 임무 유형을 입력으로 행동 옵션을 평가한다.

각 섹션은 Purpose → Input → Processing → Generated Data → Output → Design Considerations 구조를 따른다.

Internal Components

  • Policy Engine – 정의된 정책 규칙을 적용하여 권장 행동을 선택한다.
  • Action Selector – 가능한 행동 옵션(continue, restrict, monitor, abort)을 정렬한다.

Internal Flow

  1. Retrieve Impact Assessment: Mission Impact의 결과를 받아온다.
  2. Apply Policy Rules: 위험 등급과 임무 유형에 대한 조직의 규칙을 적용한다.
  3. Select Recommended Action: 가능한 행동 옵션 중 가장 적합한 권장 정책을 결정한다.
  4. Create Policy Recommendation: 선택된 행동과 근거를 문서화한다.

Input Objects

  • Impact Assessment Record – Mission Impact에서 생성된 위험 정보.
  • Policy Rules – 조직이 정의한 규칙 목록.
  • Mission Type – 임무 유형(정찰, 항로 지정 등).

Generated Objects

  • Policy Recommendation – 선택된 권장 행동(continue/restrict/monitor/abort).

Output Objects

  • Policy Recommendation → Recovery.

Interfaces

  • Policy Query API: Mission Impact 결과를 가져오는 인터페이스.
  • Policy Export API: Recovery 단계가 권장 정책을 읽는 인터페이스.

Required Tables

  • Policy Mapping Table – 위험 등급·임무 유형별 권장 행동을 요약.

Required Diagrams

  • Policy Decision Tree – 정책 규칙을 기반으로 행동 옵션을 선택하는 과정을 표현.

Failure Handling

  • 정책 규칙이 정의되지 않은 상황에서는 기본적으로 “monitor and continue” 정책을 선택하고 관리자 알림을 생성한다.
  • 정책 충돌이 발생할 경우 우선순위 규칙을 적용하거나 관리자가 수동으로 개입한다.

Cross References

  • Recovery – 권장 정책을 기반으로 복구 옵션을 생성한다.
  • Mission Decision – 정책과 복구를 종합하여 최종 결정을 내린다.

Design Notes

  • 정책 규칙은 조직의 위험 허용도와 운영 지침에 따라 지속적으로 업데이트될 수 있으며, Skeleton에는 구조만 정의한다.

Recovery

Chapter Summary

정책 추천과 신뢰 결핍 영역을 기반으로 시스템의 신뢰를 회복하거나 안전하게 운영할 수 있는 구체적인 복구 옵션을 평가하고 실행 가능성을 선택한다.

Purpose

임무를 계속 수행하기 위해 시스템을 복구하거나 필요한 경우 안전하게 축소하는 방안을 결정한다.

Scope

  • 복구 후보 생성: 재인증, 세션 재설정, 대체 링크 전환, 키 회전 등.
  • 복구 평가: 각 후보의 실행 가능성, 비용, 효과를 분석.
  • 제외: 최종 임무 결정 로직(다음 단계).

Section Tree

  • Recovery Candidates – 가능한 복구 절차 목록을 생성한다.
  • Recovery Evaluation – 후보들의 실행 가능성과 효과를 평가한다.
  • Recovery Strategy – 최적의 복구 절차를 선택한다.

각 섹션은 동일한 구조(Purpose → Input → Processing → Generated Data → Output → Design Considerations)로 작성한다.

Internal Components

  • Recovery Candidate Generator – 신뢰 결핍 영역과 정책 추천을 입력받아 복구 후보를 생성한다.
  • Feasibility Evaluator – 각 후보의 실행 가능성을 기술적·운영적 기준으로 평가한다.
  • Recovery Selector – 최적 후보를 선택한다.

Internal Flow

  1. Gather Inputs: Policy Recommendation, Trust deficits, Impact scores.
  2. Generate Candidates: Recovery Candidate Generator가 재인증, 세션 재설정, 키 회전 등 후보를 생성한다.
  3. Evaluate Candidates: Feasibility Evaluator가 실행 가능성(시간, 자원), 효과(신뢰 회복 여부), 위험을 평가한다.
  4. Select Action: Recovery Selector가 가장 적합한 복구 옵션을 선택한다.
  5. Create Recovery Decision: 선택된 복구 절차와 근거를 문서화한다.

Input Objects

  • Policy Recommendation – Policy 단계에서 선택된 행동.
  • Trust Deficits – 영역별 신뢰 부족 정보.
  • Impact Scores – 영역별 영향 정도.
  • Available Resources – 시스템에서 실행 가능한 복구에 필요한 자원 목록.

Generated Objects

  • Recovery Candidate List – 제안된 복구 옵션 목록.
  • Recovery Evaluation Report – 각 후보의 평가 결과.
  • Selected Recovery Action – 최종 선택된 복구 절차.

Output Objects

  • Selected Recovery Action → Mission Decision.

Interfaces

  • Recovery Query API: Policy와 Trust 정보를 조회하는 인터페이스.
  • Recovery Execution API: 선택된 복구 절차를 실제 시스템에 적용하는 인터페이스(다음 단계에서 정의).

Required Tables

  • Recovery Candidate Table – 후보 이름, 조건, 효과, 비용 등을 요약.
  • Recovery Evaluation Table – 각 후보의 평가 결과를 비교.

Required Diagrams

  • Recovery Flow Diagram – 후보 생성→평가→선택 과정을 시각화.

Failure Handling

  • 모든 복구 후보가 실행 불가능하거나 효과가 없을 경우 임무 결정 단계에서 조건부 임무 중단을 고려한다.
  • 실행 중 복구가 실패할 경우 롤백 절차와 대체 후보를 준비한다.

Cross References

  • Mission Decision – 복구 선택을 최종 결정에 반영한다.

Design Notes

  • 복구 옵션은 시스템 구성 요소와 실제 제약(예: 재부팅 시간이 긴 MME, 키 회전 시간)을 고려하여 현실적으로 설정한다.
  • 복구 절차는 자동화될 수 있지만, 안전상의 이유로 일부 단계는 관리자 승인을 요구할 수 있다.

Mission Decision

Chapter Summary

Policy 추천과 선택된 복구 절차, 임무 영향 정보를 종합하여 임무를 계속 수행할지, 조건부 수행할지, 중단할지를 최종 결정한다.

Purpose

임무 성공과 안전을 균형있게 고려하여 최종 임무 행동을 결정하고, 그 근거를 기록한다.

Scope

  • 정책과 복구 결과를 통합하여 최종 결정을 내린다.
  • 결정 근거와 데이터 출처를 기록하는 Auditing 메커니즘을 설계한다.
  • 제외: 복구 절차 실행 자체(Recovery 단계에서 처리).

Section Tree

  • Decision Logic – 정책과 복구를 결합하여 결정 규칙을 설계한다.
  • Rationale Recording – 결정 근거와 입력 데이터를 기록하는 방법을 정의한다.

Internal Components

  • Decision Engine – 규칙을 적용하여 임무 행동(Continue, Partial, Abort)을 선택한다.
  • Audit Logger – 결정 이유, 입력 데이터를 기록한다.

Internal Flow

  1. Consolidate Inputs: Policy Recommendation, Selected Recovery Action, Impact Assessment.
  2. Apply Decision Rules: Decision Engine이 사전 정의된 규칙에 따라 임무 행동을 선택한다.
  3. Record Rationale: Audit Logger가 결정 이유, 사용된 데이터, 선택된 옵션을 기록한다.
  4. Produce Mission Decision: 임무 결정 객체를 생성하고 Attack Mapping 단계에 전달한다.

Input Objects

  • Policy Recommendation – 추천된 행동.
  • Selected Recovery Action – 복구 단계에서 선택된 옵션.
  • Impact Assessment – 위험 등급 및 영향 점수.

Generated Objects

  • Mission Decision Object – 최종 행동 및 조건을 포함.
  • Decision Rationale – 선택 근거와 사용된 데이터.

Output Objects

  • Mission Decision Object → Attack Mapping.

Interfaces

  • Decision Export API: Attack Mapping과 End‑to‑End Architecture가 임무 결정을 가져가는 인터페이스.

Required Tables

  • Mission Decision Table – 정책, 복구, 영향, 최종 행동을 요약.

Required Diagrams

  • Decision Flow Diagram – 입력→규칙→결정→기록 과정을 도식화.

Failure Handling

  • 필수 입력이 없거나 충돌하는 경우 가장 안전한 옵션(임무 중단)을 선택하고 관리자 승인을 요구한다.
  • Audit 기록이 실패할 경우 로그를 보조 저장소에 백업한다.

Cross References

  • Attack Mapping – 임무 결정과 공격 시나리오 매핑을 위해 사용된다.
  • End‑to‑End Architecture – 전체 시스템 흐름에 결정 정보를 통합한다.

Design Notes

  • 결정 규칙은 조직의 위험 허용도와 임무 우선순위에 따라 조정할 수 있도록 설계한다.
  • 결정 근거의 투명성을 위해 모든 입력과 규칙 적용 과정을 상세히 기록해야 한다.

Attack Mapping

Chapter Summary

각 공격 시나리오와 Defense Capability·Evidence·Trust·Mission Decision 간의 관계를 매핑하여 방어 체계의 커버리지와 취약점을 평가한다.

Purpose

공격이 탐지·완화되는 경로를 명확히 하여 방어 시스템의 효과를 검증하고, 커버리지 갭을 식별한다.

Scope

  • 각 공격 시나리오가 어느 Capability, Evidence, Trust 영역을 통해 탐지되고 임무 결정을 어떻게 변화시키는지 기록한다.
  • 커버리지 갭을 식별하고 추가 Capability 또는 Evidence 요구사항을 제안한다.
  • 제외: 실제 탐지 알고리즘 세부 구현.

Section Tree

  • Mapping Matrix – 공격 시나리오와 방어 요소(Capability, Evidence, Trust, Policy, Recovery, Decision)의 매핑 표를 정의한다.
  • Coverage Analysis – 매핑 결과를 분석하여 커버리지 부족 영역을 식별한다.

Internal Components

  • Attack Catalog – 공격 시나리오 목록과 특성을 유지한다.
  • Mapping Builder – 각 공격에 대한 Detection path를 구성한다.
  • Coverage Analyzer – 매핑 결과를 분석하여 방어 결함을 찾는다.

Internal Flow

  1. Import Attack Catalog: 공격 시나리오 목록과 특성을 로드한다.
  2. Build Mappings: 각 공격을 어떤 Capability, Evidence, Trust 평가가 탐지하는지 매핑한다.
  3. Analyze Coverage: Mapping Builder의 출력에서 커버리지 갭(탐지 불가 영역)을 식별한다.
  4. Produce Mapping Matrix: 공격 시나리오, 탐지 경로, 결과 임무 결정을 표 형태로 정리한다.

Input Objects

  • Attack Scenarios – TM1/V2, TM2, TM3, NF-3, NF-4, NF-6 등 시나리오 목록【488147192654095†L60-L99】.
  • Capability Definitions – 각 Capability와 모니터링 메트릭.
  • Evidence Records – 탐지된 이벤트.
  • Mission Decisions – 결정 결과.

Generated Objects

  • Attack‑to‑Capability Mapping – 각 공격이 어느 Capability에서 탐지되는지 매핑.
  • Coverage Gap List – 탐지되지 않거나 대응이 부족한 공격.
  • Mapping Matrix – 공격, Detection path, 임무 결정 결과를 포함한 표.

Output Objects

  • Mapping Matrix → End‑to‑End Architecture.

Interfaces

  • Attack Catalog API: 공격 시나리오 목록을 조회하는 인터페이스.
  • Mapping Query API: 다른 장이 매핑 결과를 조회하는 인터페이스.

Required Tables

  • Attack Mapping Matrix – 공격, 감지 Capability, Evidence, Trust 영역, 정책/복구, 임무 결정 결과를 6열로 정리.

Required Diagrams

  • Mapping Diagram – 공격에서 임무 결정까지의 탐지·완화 경로를 시각화.

Failure Handling

  • 공격 시나리오가 충분히 문서화되지 않은 경우, 해당 공격을 커버리지 분석에서 제외하거나 별도 조사 필요성을 기록한다.
  • 매핑이 불가능한 경우(예: 새로운 공격), Capability 확장 또는 추가 Evidence 필요성을 End‑to‑End Architecture에서 논의한다.

Cross References

  • End‑to‑End Architecture – 전체 방어 체계의 통합 시 공격 매핑 정보를 사용한다.
  • Defense Capability – 매핑을 통해 Capability 설계가 적절한지 피드백한다.

Design Notes

  • Mapping Matrix는 지속적으로 업데이트되어야 하며, 새로운 공격에 대한 방어 커버리지 평가에 활용된다.
  • 매핑 결과를 통해 방어 체계의 우선 개선 영역을 도출한다.

End‑to‑End Architecture

Chapter Summary

모든 장의 입력과 출력, 데이터 흐름, 모듈 상호작용을 종합하여 전체 Mission‑Centric Defense Architecture를 한눈에 보여준다.

Purpose

Threat Analysis부터 Mission Decision까지의 파이프라인과 Attack Mapping 결과를 통합하여 방어 체계의 전반적인 구조를 설명한다.

Scope

  • 모든 데이터 객체의 흐름과 모듈 간 인터페이스를 정리한다.
  • 각 장의 역할과 상호 의존성을 도식화한다.
  • 제외: 개별 모듈의 내부 알고리즘 세부 사항.

Section Tree

  • Overall Pipeline – Threat Analysis부터 Mission Decision까지의 연속 흐름을 설명한다.
  • Component Interactions – 각 모듈 간 호출 및 데이터 교환 관계를 정리한다.

Internal Components

  • Pipeline Integrator – 각 장의 출력과 입력을 연결하는 연결 로직.
  • Interface Catalog – 모든 인터페이스와 데이터 객체의 정의를 저장한다.
  • Visualization Generator – 종합 아키텍처 다이어그램을 생성한다.

Internal Flow

  1. Collect Artifacts: 각 장에서 정의한 데이터 객체, 인터페이스, 흐름을 수집한다.
  2. Map Pipeline: 입력과 출력의 연결 관계를 분석하여 연속 파이프라인을 구성한다.
  3. Define Interactions: 모듈 간 호출 순서와 데이터 교환을 기록한다.
  4. Generate Integrated View: 도표와 설명을 통해 End‑to‑End Architecture를 작성한다.

Input Objects

  • All Chapter Outputs – 각 장에서 생성된 모든 데이터 객체와 정의.
  • Attack Mapping Matrix – 공격과 방어 경로 매핑.

Generated Objects

  • Integrated Architecture Document – 전체 방어 체계 설명.
  • End‑to‑End Diagrams – 파이프라인 다이어그램, 모듈 상호작용 도표.

Output Objects

  • Integrated Architecture Document – 최종 설계 문서의 기반.

Interfaces

  • Artifact Repository: 각 장의 결과물을 저장·조회하는 인터페이스.
  • Visualization API: Diagram 생성 도구와 연동하는 인터페이스.

Required Tables

  • Component List – 모든 모듈과 담당 기능을 요약.
  • Data Flow Table – 데이터 객체와 이동 경로를 요약.

Required Diagrams

  • End‑to‑End Architecture Diagram – 전체 시스템과 데이터 흐름을 한눈에 보여준다.
  • Interaction Diagram – 모듈 간 호출 관계를 시퀀스 형태로 표현한다.

Failure Handling

  • 연결 관계에 모순이나 누락이 발견될 경우, 원 장에 피드백을 제공하고 Skeleton을 업데이트한다.

Cross References

  • 모든 Chapter – End‑to‑End Architecture는 각 장의 정의를 참조하여 구성된다.

Design Notes

  • End‑to‑End 시각화는 독자가 전체 방어 흐름을 빠르게 이해할 수 있도록 간결하고 일관된 표현을 사용한다.
  • 모듈 간 인터페이스 정의는 추후 코드 설계에 직접 활용될 수 있도록 명확해야 한다.
본 Skeleton 문서는 Mission‑Centric Defense Architecture 상세 설계의 기반이 되는 내부 구조를 정의한다. 각 Chapter는 테스트베드에서 실제로 수집 가능한 데이터와 공격 시나리오에서 검증된 위협만을 입력으로 사용하며, 보안 속성에 기반한 Capability 중심 설계를 관통한다. Skeleton을 바탕으로 후속 단계에서 알고리즘, 임계값, 규칙을 상세화하여 자동 방어 시스템을 구현할 수 있다.
