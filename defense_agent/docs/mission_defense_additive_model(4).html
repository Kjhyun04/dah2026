1. Additive Model Overview

본 문서는 Core Architecture Model을 보완하는 추가 모델을 정의한다. 기존 Chapter와 객체, 구조를 변경하지 않고, Mission‑Centric Defense Architecture의 완성도를 높이기 위한 데이터 모델과 평가 구조를 추가한다. 다음에 제시되는 모델들은 테스트베드에서 측정 가능한 지표와 실증된 공격 시나리오의 특성을 기반으로 설계되며, 모든 Chapter에서 공통적으로 사용될 수 있도록 표준화되어 있다.

추가 모델은 Threshold Policy, Time Window, Evidence Correlation, Recovery Feasibility, Decision Trace, Core Data Flow, 그리고 Mission Decision (Revision)의 7가지로 구성된다. 각각의 모델은 명확한 입력·출력·관계를 규정하여 방어 에이전트 설계 시 추가 데이터 구조 정의가 필요 없도록 한다.

2. Threshold Policy Model

Purpose

Threshold Policy Model은 아키텍처 전반에서 사용하는 모든 메트릭의 판단 기준을 통일하기 위해 설계된다. 각 메트릭에 대해 정상(Normal), 경고(Warning), 심각(Critical), 위험(Danger)의 범위를 정의하여 Evidence 생성, Trust 계산, Policy 평가 및 Recovery 판단이 일관된 기준을 따르도록 한다.

Why Required

테스트베드와 공격 시나리오 분석에 따르면 PFCP 세션 삭제, 웹 API 무인증 요청, MongoDB 접근, NAS 암호 설정 등 다양한 메트릭이 방어 판단에 직접 영향을 미친다【208159606947672†L279-L293】. 각 Capability가 개별적으로 임계치를 정의하면 도메인 간 비교가 어렵기 때문에, 모든 메트릭을 하나의 정책 표준으로 관리할 필요가 있다.

Inputs

  • Metric Definitions: 테스트베드에서 측정 가능한 메트릭 이름과 단위(예: Packet Loss(%), RTT(ms), PFCP_Delete_Attempt(건), NAS_Cipher_Order, Auth_Failure(횟수), DB_Access(횟수), Unauthorized_Command(건), Session_Reset(건)).
  • Baseline Values: 각 메트릭에 대한 정상(expected) 값과 설계상 허용되는 변동 폭. 예를 들어 PFCP 세션 삭제 시도는 0이 정상이고, NAS 암호 설정은 EEA2 우선 순위가 정상이다【208159606947672†L279-L293】.
  • Mission Weight and Severity Mapping: Mission Weight Model에서 정의한 가중치와 각 메트릭의 공격 영향도를 나타내는 severity factor.
  • Time Window Parameters: 평가 시 사용할 관찰 창, 롤링 창 등의 시간 매개변수. 이는 Time Window Model과 연계된다.

Internal Fields

Threshold Policy Model은 각 메트릭에 대해 다음 필드를 정의한다. 모델은 표 형식으로 관리되며, 새로운 메트릭이 추가될 경우 동일한 구조를 확장한다.

FieldTypeDescription
metricstring메트릭 이름. 예: PFCP_Delete_Attempt, DB_Access, Unauthorized_Command.
unitstring측정 단위(건/초, %, ms 등).
normal_rangerange/any정상 상태로 간주되는 값 또는 값의 범위. 예: 0 PFCP_Delete_Attempt.
warning_rangerange/any경고로 분류되는 값의 범위. 예: PFCP_Delete_Attempt가 1 건일 때.
critical_rangerange/any심각으로 분류되는 값의 범위. 예: MongoDB Access가 인증 없이 1 회 이상 발생.
danger_rangerange/any위험으로 분류되는 값의 범위. 예: NAS_Cipher_Order가 EEA0로 설정되거나 키 유출이 탐지된 경우.

Relationships

Threshold 값은 Evidence Object가 관측값과 비교하여 severity를 결정하는 데 사용된다. Trust Score Model은 severity와 weight를 사용하여 각 도메인의 신뢰 점수를 계산하고, Policy와 Recovery 단계는 동일한 임계치를 참조하여 경보 수준에 따른 대응을 결정한다. Threshold Policy Model은 Time Window Model에서 정의한 평가 구간과 연계되어 실시간 또는 롤링 기준으로 판단한다.

Processing Logic

  • 메트릭이 발생하면 Threshold Repository에서 해당 메트릭의 정의를 조회한다.
  • Observation Window 또는 Current Snapshot에서 관측된 값이 각 범위에 속하는지 비교하고 severity를 지정한다.
  • 지정된 severity에 따라 Evidence Object의 severity 필드가 설정되고, Trust 평가와 Policy 판단에서 가중치를 적용한다.
  • Threshold 표는 주기적으로 테스트베드에서 측정한 정상값을 기반으로 조정될 수 있으며, 임무 유형 또는 환경에 따라 Mission Weight Model과 연계하여 동적으로 재설정된다.

Outputs

각 메트릭에 대한 severity classification과 해당 임계치 설명을 포함한 결과. 이 결과는 Evidence Object와 Trust Architecture에 전달된다.

Design Considerations

  • 모든 임계치는 테스트베드 실측 값과 공격 시나리오 결과를 기반으로 설정한다. 예를 들어 PFCP Delete, DB Access, Unauthorized Command 등은 실제 공격에서 단일 시도만으로 치명적 영향을 미치므로 위협 범위를 매우 낮게 설정한다【574666281232364†L162-L176】.
  • Mission 유형, 우선순위에 따라 메트릭의 중요도가 달라질 수 있다. Mission Weight Model과 연계하여 임계치를 조정한다.
  • Threshold 설정은 과도한 false positive를 방지하기 위해 시간 창과 함께 사용된다(Time Window Model 참조).
  • 정상(Normal) 범위를 명확히 정의하지 않으면 경보 폭주가 발생할 수 있으므로, 테스트베드 데이터로 학습된 기대값을 사용한다.

3. Time Window Model

Purpose

Time Window Model은 단일 이벤트뿐 아니라 일정 기간 동안의 변화와 패턴을 평가할 수 있도록 시간 창을 정의한다. 평가 시점의 현재 상태와 최근 변동을 함께 고려하여 보다 정확한 신뢰 평가와 임팩트 분석을 가능하게 한다.

Why Required

다수의 공격은 짧은 기간 동안 연속적으로 발생하거나 서서히 악화되는 패턴을 보인다. PFCP 세션 삭제, 불법 명령 주입, DB 스캔 등은 일정 시간 내 반복적인 시도가 탐지되어야 한다【574666281232364†L162-L176】. Time Window Model을 사용하면 Evidence Object와 Trust Architecture에서 이러한 패턴을 인식하고 false positive를 줄일 수 있다.

Inputs

  • Event Timestamps: Capability Monitor가 생성한 원시 이벤트의 시간 정보.
  • Window Parameters: Mission 정책과 각 메트릭의 특성에 따라 정의된 관찰 창(Observation Window), 롤링 창(Rolling Window), 집계 창(Aggregation Window), TTL(Time‑to‑Live) 값.
  • Sampling Interval: 데이터 수집 주기. 예를 들어 Packet Loss와 RTT는 밀리초 단위, DB Access는 초 단위로 샘플링한다.
  • Threshold Policy: 임계치 모델에서 정의한 값과 함께 사용하여 시간적 변동을 평가한다.

Internal Fields

FieldTypeDescription
window_typeenumcurrent_snapshot, rolling_window, observation_window, aggregation_window 중 하나.
window_sizeinteger시간 창의 크기(초). 예: rolling_window=10초.
sampling_intervalinteger데이터 수집 주기(초 또는 ms). 예: RTT=100 ms, DB_Access=1 s.
ttlintegerEvidence나 지표가 유효한 기간(초). TTL이 경과하면 평가에서 제외한다.
start_timedatetime창의 시작 시각(ISO 8601).
end_timedatetime창의 종료 시각.
aggregated_valueany창 내에서 계산된 집계 값(평균, 최대, 합 등). Trust 계산과 Threshold 평가에서 사용한다.

Relationships

Time Window Model은 Evidence Object 생성 시 이벤트를 어느 창에 속하는지 지정하고, Threshold Policy Model과 연계하여 severity를 판정한다. Rolling Window와 Observation Window는 Evidence Correlation Model에서 여러 이벤트를 하나의 Incident로 묶을 때 사용되며, Aggregation Window는 Trust Architecture와 Mission Impact 계산 시 신뢰 벡터를 도출하는 데 활용된다. TTL 값은 Evidence가 만료되는 시점을 정의하여 과거 데이터가 과도하게 영향을 미치지 않도록 한다.

Processing Logic

  • Current Snapshot: 단일 이벤트나 메트릭의 현재 값을 평가한다. 주로 즉각적인 경보에 사용된다.
  • Rolling Window: 길이 window_size의 슬라이딩 창에서 이벤트를 누적하고 평균이나 최대값을 계산한다. 예: 10 초 동안 PFCP Delete Attempt의 횟수.
  • Observation Window: Correlation Model에서 여러 Evidence를 동일 Incident로 묶기 위해 사용하는 시간 범위. 예: 5 초 내 PFCP Delete와 Unauthorized Command가 발생하면 동일 Incident로 처리.
  • Aggregation Window: Trust Architecture에서 신뢰 벡터를 산출하기 위해 사용. 예: 최근 60 초 동안의 평균 Packet Loss와 RTT를 기반으로 신뢰 점수 계산.
  • 모든 창은 sampling_interval에 따라 데이터를 수집하며, TTL이 초과하면 이전 데이터는 평가에서 제외된다.

Outputs

각 시간 창에 대해 집계된 메트릭 값과 해당 창에 속한 Evidence 목록. 이러한 출력은 Threshold Policy Model, Evidence Correlation Model, Trust Architecture 및 Mission Impact 계산에 사용된다.

Design Considerations

  • 창의 크기와 샘플링 간격은 메트릭의 특성에 따라 다르게 설정해야 한다. 예: PFCP Delete는 짧은 창(5–10 초)이 적합하고, Packet Loss는 긴 창(1–5 분)이 적합하다.
  • Observation Window가 너무 길면 연관 없는 이벤트가 묶여 false correlation이 발생할 수 있고, 너무 짧으면 멀티스텝 공격을 인지하지 못한다.
  • TTL은 Evidence의 수명을 제어하는 핵심 값이며, 임무 단계나 임무 우선순위에 따라 조정될 수 있다.
  • 시간 창은 시스템 리소스에 영향을 미치므로, 실시간 감시와 히스토리컬 분석 사이에서 균형을 맞춰야 한다.

Example Structure

{
  "window_type": "rolling_window",
  "window_size": 10,
  "sampling_interval": 1,
  "ttl": 60,
  "start_time": "2026-07-05T15:30:00Z",
  "end_time": "2026-07-05T15:30:10Z",
  "aggregated_value": 2
}

4. Evidence Correlation Model

Purpose

Evidence Correlation Model은 서로 연관된 여러 Evidence를 하나의 Incident로 묶어 공격 패턴을 더 잘 이해할 수 있도록 한다. 단일 이벤트로는 파악하기 어려운 다단계 공격과 사이드 이펙트를 식별하기 위해 상관 분석 규칙과 Incident 객체 구조를 정의한다.

Why Required

공격 시나리오에서는 PFCP 세션 삭제와 MAVLink 명령 주입이 짧은 시간 안에 연속해서 발생하거나, 동일한 IP에서 여러 Capability 이벤트가 발생하는 경우가 있다【574666281232364†L162-L176】. 이러한 증거를 개별적으로 처리하면 공격의 맥락을 놓칠 수 있으므로, 공통된 속성 및 시간 조건에 따라 사건을 묶어야 한다.

Inputs

  • Evidence Records: Evidence Object에서 생성된 레코드 목록. 각 레코드는 evidence_id, timestamp, capability, source, entity, metric, severity를 포함한다.
  • Correlation Rules: 상관 규칙 정의. 각 규칙에는 조건(예: 시간 간격, 동일 IP, 동일 Capability, 특정 메트릭 조합)과 상관 점수 계산 방법이 포함된다.
  • Time Window Parameters: Observation Window와 Rolling Window 크기. 규칙 평가 시 사용된다.
  • Threshold Policy: 중복된 증거를 필터링하기 위한 severity 임계값. 매우 낮은 심각도의 이벤트는 상관에서 제외할 수 있다.

Internal Fields

Evidence Correlation Model은 두 개의 주요 구조를 정의한다: Correlation Rule과 Incident Object.

Relationships

Evidence Correlation Model은 Evidence Object에서 상관 ID를 채워 Incident와 연결하고, Incident Object는 Trust Architecture에서 도메인별 신뢰 점수를 계산할 때 입력으로 사용된다. Incident 정보는 Decision Trace Model에서도 기록되어 최종 판단의 근거가 된다. Correlation Rules는 Threshold Policy Model과 Time Window Model을 참고하여 평가된다.

Processing Logic

  • Correlation 엔진은 Observation Window 내에서 Evidence를 수집한다.
  • 각 Correlation Rule에 대해 규칙의 조건을 만족하는 Evidence 집합을 찾는다. 예: 동일한 source와 target을 가진 PFCP_Delete_Attempt와 Unauthorized_Command가 5 초 이내에 발생하면 규칙 ID = CR01이 성립한다.
  • 집합이 조건을 만족하면 Incident를 생성하고, 해당 Evidence의 correlation_id를 Incident ID로 업데이트한다.
  • Incident의 correlation_score는 규칙의 correlation_score_weight와 Evidence의 severity를 바탕으로 계산한다. 여러 규칙이 적용될 경우 합산한다.
  • 생성된 Incident는 Incident Repository에 저장되고 Trust Architecture가 이를 조회한다.

Outputs

Incident Object 리스트와 각 Incident의 correlation_score. 증거 간의 연관성을 설명하는 메타데이터는 Trust Architecture와 Decision Trace Model로 전달된다.

Design Considerations

  • 상관 규칙은 테스트베드에서 관측된 패턴과 공격 시나리오를 기반으로 정의한다. 예: PFCP Delete와 Unauthorized Command의 연계는 TM2·NF‑4 시나리오에서 반복 관측되었다【574666281232364†L162-L176】.
  • Incident의 크기가 너무 크면 공격 단계가 분리되지 않고, 너무 작으면 매 단계의 연계가 놓칠 수 있다. 상관 점수는 정책과 회복 판단에서 가중치로 사용되므로 적절한 스케일링이 필요하다.
  • Correlation Score는 정규화(0–1)하여 다른 평가 모델과 결합하기 쉽게 한다.
  • 증거의 심각도가 낮거나 시간이 많이 지난 경우 상관에서 제외하거나 가중치를 낮출 수 있다.

Example Structure

{
  "rule_id": "CR01",
  "description": "PFCP deletion and unauthorized command within 5 seconds from same source",
  "conditions": {
    "capabilities": ["session_network", "command"],
    "metrics": ["PFCP_Delete_Attempt", "Unauthorized_Command"],
    "max_time_diff": 5,
    "attribute_match": "source_ip"
  },
  "correlation_score_weight": 0.7,
  "severity_threshold": "warning"
}
{
  "incident_id": "INC20260705-0003",
  "rule_id": "CR01",
  "evidence_ids": ["EV20260705-0001", "EV20260705-0007"],
  "source": "10.44.0.17",
  "target": "net_core_UPF",
  "capability": "session_network",
  "start_time": "2026-07-05T15:30:05Z",
  "end_time": "2026-07-05T15:30:09Z",
  "correlation_score": 0.85,
  "description": "PFCP session deletion followed by an unauthorized command to web_backend within 4 seconds."
}

5. Recovery Feasibility Model

Purpose

Recovery Feasibility Model은 복구 후보의 실행 가능성을 정량적으로 평가하여 Mission Decision 단계에서 우선순위를 결정할 수 있도록 한다. 단순히 복구 옵션을 나열하는 것이 아니라, 실행 시간, 자원 비용, 신뢰 회복 효과, 임무 회복 효과, 성공 확률, 위험도를 종합하여 Recovery Score를 산출한다.

Why Required

PFCP 세션 재생성, 세션 재attach, 서명 키 회전, 임무 재구성 등 다양한 복구 방법이 존재하지만, 실제로는 임무 시간과 자원이 한정되어 있다. 테스트베드와 공격 시나리오 분석 결과, 일부 복구는 시간이 오래 걸리거나 임무를 방해할 수 있다【574666281232364†L162-L176】. Recovery Feasibility Model은 이러한 요소를 체계적으로 비교하여 가장 적절한 복구를 선택하기 위해 필요하다.

Inputs

  • Candidate Recovery Actions: Policy 단계에서 생성된 복구 후보. 각 후보에는 recovery_id와 recovery_type이 포함된다.
  • Trust and Mission Impact: 현재 신뢰 벡터와 임무 영향 평가 결과. 회복이 어느 도메인에 어떤 영향을 줄지 예측하기 위해 사용된다.
  • Resource Availability: 네트워크 대역폭, 프로세싱 파워, 배터리 잔량 등 현재 시스템 자원 상태.
  • Mission Constraints: 임무의 우선순위, 종료 시각, 환경 제약 등 Mission Context Object의 요소.
  • Historical Success Data: 과거 복구 실행의 성공/실패 이력과 평균 소요 시간 등. 성공 확률 추정에 사용한다.

Internal Fields

Recovery Feasibility Model은 각 복구 후보에 대해 다음 필드를 계산하여 Recovery Object를 확장한다.

FieldTypeDescription
recovery_idstring복구 후보 식별자. Policy 단계에서 생성.
recovery_typestring복구 유형. 예: session_reconnect, key_rotation, command_filtering, mission_replan, safe_landing.
execution_timefloat복구 작업을 수행하는 데 걸리는 예상 시간(초).
mission_delayfloat임무 일정에 미치는 지연(초 또는 %).
resource_costfloat복구 실행에 필요한 자원 비용(정규화 0–1). 예: CPU/메모리/배터리 소모.
expected_trust_recoverydict도메인별 신뢰 회복 예상치. 예: {"session_network": +20, "command": +10}.
expected_mission_recoveryfloatMission Impact 점수 감소량 또는 향상 예상치.
success_probabilityfloat복구가 성공할 확률(0–1). 경험적 데이터와 조건 기반 추정.
recovery_riskfloat복구 중 발생 가능한 부작용 위험(0–1). 예: 실행 실패시 추가 장애 발생 가능성.
recovery_scorefloat위 요소를 가중합하여 계산한 종합 점수(0–1). 값이 높을수록 우선순위가 높다.

Relationships

Recovery Feasibility Model은 Policy Rule Object에서 정의된 조치들과 Mission Impact 결과를 받아 Recovery Object를 확장한다. 계산된 recovery_score는 Mission Decision Model에서 선택 순서를 결정하는 데 사용된다. Execution Time과 Mission Delay는 Time Window Model과 Mission Context Object에 정의된 제한과 연계된다. Expected Trust Recovery는 Trust Object와 Mission Impact Model의 연동을 통해 추정한다.

Processing Logic

  • 각 복구 후보에 대해 Execution Time, Mission Delay, Resource Cost를 파악한다. 테스트베드에서 측정된 평균값과 시스템 상태를 기반으로 추정한다.
  • Trust Object와 Mission Impact Object를 분석하여 해당 복구가 도메인 신뢰 및 임무 임팩트에 미치는 예상 회복량을 산출한다.
  • Success Probability와 Recovery Risk를 과거 실행 데이터와 환경 요인(예: 네트워크 혼잡, 서명 키 배포 현황)을 통해 추정한다.
  • Recovery Score = f(expected_trust_recovery, expected_mission_recovery, success_probability, 1-recovery_risk, 1-mission_delay, 1-resource_cost). 가중치는 임무 중요도와 Mission Weight에 따라 조정된다.
  • 모든 후보에 대해 Recovery Score를 계산하여 우선순위 목록을 생성한다.

Outputs

각 복구 후보에 대해 계산된 recovery_score와 확장된 Recovery Object. 이 정보는 Mission Decision Model에서 가장 적합한 복구를 선택하는 데 사용된다.

Design Considerations

  • 복구가 장시간 임무에 끼치는 영향은 단순한 지연 이상의 의미를 갖는다. 예: 정찰 임무에서는 짧은 지연도 기회를 놓칠 수 있으므로 mission_delay 가중치를 높게 설정한다.
  • Expected Trust Recovery와 Expected Mission Recovery는 모델링에 기반하며, 실제 결과와 차이가 발생할 수 있다. Decision Trace Model에서 결과를 기록해 향후 조정을 가능하게 한다.
  • Recovery Risk는 복구 자체가 새로운 취약점을 만들 수 있음을 고려한다. 예: 키 회전은 잠재적으로 재발급 과정에서 키 유출 위험을 증가시킬 수 있다.

Example Structure

{
  "recovery_id": "RC20260705-01",
  "recovery_type": "session_reconnect",
  "execution_time": 30.0,
  "mission_delay": 30.0,
  "resource_cost": 0.2,
  "expected_trust_recovery": {"session_network": 25, "command": 10},
  "expected_mission_recovery": 0.6,
  "success_probability": 0.8,
  "recovery_risk": 0.1,
  "recovery_score": 0.78
}

6. Decision Trace Model

Purpose

Decision Trace Model은 각 Mission Decision이 어떤 근거와 과정을 통해 도출되었는지 추적하기 위해 설계된다. Evidence부터 최종 결정까지의 모든 단계와 데이터를 기록하여, 의사 결정의 투명성과 감사 가능성을 확보한다.

Why Required

방어 시스템의 신뢰성과 책임성을 확보하려면, 각 결정에 대한 설명 가능한 근거를 제공해야 한다. 공격 대응이나 임무 중단과 같은 중대한 결정을 다시 검토하거나 감독 기관에 보고할 때 Decision Trace가 필요하다. 또한 추후 Threshold와 Policy 조정에 활용된다.

Inputs

  • Evidence Chain: 사건에 사용된 Evidence ID 목록과 각각의 severity, timestamp.
  • Trust Chain: 도메인별 Trust Object와 신뢰 점수, Confidence.
  • Mission Context: Mission Context Object의 전체 필드.
  • Mission Impact: Mission Impact Object와 임무 리스크 평가.
  • Policy Rule: 적용된 Policy Rule ID와 선택된 Action, 예외 항목.
  • Recovery Plan: 선택된 Recovery Object와 Recovery Score, 이유.
  • Decision Metadata: 최종 Mission Decision 카테고리, Confidence, Timestamp.

Internal Fields

FieldTypeDescription
decision_idstring결정 기록의 고유 ID.
mission_idstring해당 임무의 식별자.
timestampdatetime결정이 내려진 시각.
evidence_chainlist<string>Decision에서 고려된 Evidence ID 목록.
trust_chaindict도메인별 Trust Score, Confidence, Reason.
mission_contextobjectMission Context Object의 스냅샷.
mission_impactobjectMission Impact Object와 Mission Risk 값.
policy_ruleobject적용된 Policy Rule: rule_id, priority, condition, action.
recovery_planobject선택된 Recovery Object와 Recovery Score, 이유.
decisionstring최종 Mission Decision 카테고리.
confidencefloat해당 결정에 대한 신뢰도(0–1).
trace_stepslist<string>Evidence→Trust→Mission Context→Impact→Policy→Recovery→Decision의 서술적 설명.

Relationships

Decision Trace Model은 Mission Decision Model의 부수 산출물로 생성되며, 모든 앞 단계 모델과 연결된다. Evidence Correlation으로부터 Incident 정보를 포함하고, Trust Object와 Mission Impact Object를 요약한 내용, Policy Rule과 Recovery 후보 평가를 포함하여 하나의 기록으로 보존한다. 이는 감사 로그로 저장되며, Threshold와 Policy 조정 시 참조된다.

Processing Logic

  • Mission Decision 단계에서 Decision Trace Object를 초기화하고 decision_id와 timestamp를 생성한다.
  • 해당 결정에 사용된 Evidence 목록과 Incident 정보를 evidence_chain에 기록하고, 도메인별 Trust Score와 Reason을 trust_chain에 기록한다.
  • Mission Context와 Mission Impact를 스냅샷으로 저장한다.
  • 적용된 Policy Rule과 선택된 Recovery Plan을 기록하고, Trace Steps 배열에 각 단계와 이유를 서술한다.
  • Confidence 값은 Trust Score Confidence와 Recovery Feasibility Success Probability 등을 종합하여 계산한다.
  • 결정 기록은 무결성 보호를 위해 해시 또는 서명하여 저장하며, 향후 분석과 감사에서 사용된다.

Outputs

Decision Trace Object. 이 객체는 감사 로그 시스템이나 비행 기록과 함께 저장되어, 나중에 의사 결정 과정의 검증에 사용된다.

Design Considerations

  • Trace Object는 데이터 크기가 커질 수 있으므로, 요약 버전과 상세 버전을 구분하여 저장할 수 있다.
  • 민감 정보(예: K/OPc 등)는 암호화하거나 마스킹하여 기록하며, 접근 권한을 제한한다.
  • Trace Steps는 사람이 이해할 수 있도록 서술형 문장으로 작성하되, 자동 생성이 가능한 구조를 고려한다.
  • 의사 결정 투명성을 보장하기 위해 모든 결정에 대해 Trace 생성이 필수이며, 실패 시 경고를 발생시킨다.

7. Core Data Flow Model

Purpose

Core Data Flow Model은 Mission‑Centric Defense Architecture 내에서 객체가 어떻게 생성되고 이동하는지를 정형화한다. 이 모델은 각 단계의 프로듀서와 컨슈머를 명시하여 End‑to‑End 파이프라인을 이해하고 구현할 수 있도록 지원한다.

Why Required

각 Chapter가 독립적으로 설계되더라도, 데이터가 어떤 경로를 통해 흐르는지 명확히 정의하지 않으면 연결성이 붕괴된다. Core Data Flow Model은 Capability에서 발생한 데이터가 Evidence, Trust, Mission Context, Mission Impact, Policy, Recovery, Mission Decision에 이르기까지 단계별로 어떻게 전달되는지 설명한다.

Inputs

이 모델 자체는 입력이 없다. 대신 Core Model에서 정의된 모든 객체(Evidence, Trust, Mission Context, Mission Impact, Policy Rule, Recovery, Mission Decision)를 대상으로 한다.

Internal Fields

Relationships

각 단계는 이전 단계의 출력 객체를 입력으로 사용하며, 프로듀서와 컨슈머를 명확히 정의함으로써 모듈화된 구현과 교차 검증이 가능해진다. Evidence Correlation과 Trust Evaluation은 Time Window Model과 Threshold Policy Model을 참조하고, Mission Impact 계산은 Mission Weight Model과 Confidence Model을 참조한다. Recovery Planner는 Recovery Feasibility Model을 호출하여 점수화된 회복을 제공하고, Mission Decision Engine은 Decision Trace Model을 생성한다.

Processing Logic

데이터 흐름은 순차적으로 진행되나, 일부 단계는 비동기적으로 실행될 수 있다. 예를 들어 Evidence Collection과 Correlation은 실시간 스트림으로 처리하고, Trust Evaluation과 Impact Calculation은 일정 간격으로 배치 처리할 수 있다. 흐름의 무결성을 유지하기 위해 각 객체에는 고유 ID와 타임스탬프가 포함되며, 추적성을 확보한다.

Outputs

정의된 데이터 흐름 표와 단계별 프로듀서·컨슈머 정의. 이 표는 아키텍처 구현과 문서화의 기준으로 사용된다.

Design Considerations

  • 데이터 흐름은 기밀성·무결성·가용성 보장을 위해 암호화 및 인증 메커니즘을 포함해야 한다.
  • 각 단계 간 인터페이스는 명확히 정의되어야 하며, 객체 스키마와 네트워크 프로토콜을 문서화해야 한다.
  • 병렬 실행 시 동기화 문제를 고려하여, Evidence와 Incident의 순서가 보존되도록 타임스탬프와 시퀀스 번호를 사용한다.
  • 로그 및 감사용 메타데이터를 각 객체에 포함시켜 Decision Trace와 연계한다.

Example Structure

위 표 자체가 Core Data Flow Model의 예시이다. 추가 예로, PFCP Delete Attempt가 탐지된 후의 흐름은 다음과 같다:

Capability(session_network) → Evidence Object(EV20260705-0001) → Correlation Engine → Incident(INC20260705-0003) → Trust Evaluator → Trust Object( session_network_score = 40 ) → Mission Impact Evaluator → Mission Impact(availability=0.6) → Policy Engine(continue + monitor) → Recovery Planner(session_reconnect) → Mission Decision(Continue + Monitoring) → Decision Trace 기록.

8. Mission Decision Model (Revision)

Purpose

Mission Decision Model (Revision)은 기존의 세 가지 결정(Continue, Partial, Abort)을 여섯 가지로 확장하여 임무 상태에 따른 세분화된 대응을 가능하게 한다. 이를 통해 방어 에이전트가 신뢰와 임무 위험, 복구 가능성을 종합하여 더 유연한 결정을 내릴 수 있다.

Why Required

공격 영향이 항상 임무 중단을 의미하지는 않는다. 공격이 단일 영역에 국한되거나 빠르게 복구 가능한 경우 임무를 계속하면서도 추가 감시나 재구성이 필요할 수 있다. 확장된 결정 모델은 Mission Impact와 Recovery Feasibility를 고려하여 적절한 대응을 선택하도록 설계된다【574666281232364†L162-L176】.

Inputs

  • Mission Impact: Mission Impact Object의 overall_impact, 각 영역별 영향도, Mission Risk.
  • Trust Vector: 도메인별 Trust Object와 Confidence.
  • Recovery Feasibility: Recovery Object의 Recovery Score와 예상 회복량.
  • Policy Conditions: Policy Rule Object에서 정의한 조건과 우선순위.
  • Mission Context: 임무 유형, 우선순위, 단계 및 환경 제약.

Internal Fields

Mission Decision Model은 다음 여섯 가지 결정 카테고리를 정의하고, 각 카테고리에 대한 조건을 정한다:

DecisionDescriptionApplicable Conditions
Continue 임무를 변경 없이 지속한다. Mission Risk가 낮음(예: overall_impact ≥ 0.8), Trust Scores가 각 도메인에서 높은 범위(≥70), Recovery 필요성이 없음.
Continue + Monitoring 임무를 지속하되 감시를 강화한다. Mission Risk가 보통 수준, 신뢰가 50–70 사이이거나 특정 도메인에서 경고/critical 수준. Recovery Score가 높지만 지금 즉시 실행할 필요가 없을 때.
Mission Reconfiguration 임무를 재구성하여 공격 영역을 우회하거나 임무 경로를 변경한다. Mission Risk가 중간 이상, Trust가 낮은 도메인이 있으나 완전 중단 필요성은 없는 경우. Recovery Feasibility에서 재구성이 높은 점수를 받은 경우.
Graceful Degradation 임무 범위를 축소하거나 일부 기능을 제한하여 안전성을 확보한다. Mission Risk가 높음, Trust가 여러 도메인에서 낮고 Recovery Score가 중간 이하. 하지만 임무의 일부 목표는 달성할 수 있을 때.
Operator Confirmation 자동 결정 대신 사람이 상황을 검토하고 승인·중단 여부를 결정한다. Mission Risk가 높음 또는 극히 높음, 신뢰와 회복 가능성에 대한 불확실성이 큰 경우. 법적·안전 요구 사항으로 인해 인간 판단이 필요할 때.
Mission Abort 임무를 즉시 중단하고 안전하게 귀환한다. Mission Risk가 매우 높음(overall_impact ≤ 0.4), Trust Scores가 대부분 도메인에서 30 미만, Recovery Feasibility가 낮거나 복구가 임무 기간 내 불가능한 경우.

Relationships

Mission Decision Model은 Mission Impact Object, Trust Vector, Recovery Feasibility, Policy Rules, Mission Context를 통합하여 최종 결정을 내린다. 결정 후 Decision Trace Model을 생성하며, 선택된 결정은 실행 모듈과 오퍼레이터에게 전달된다. 각 결정은 Threshold Policy Model과 Time Window Model에서 정의된 값을 기반으로 실제 값과 비교하여 선택된다.

Processing Logic

  • Mission Impact를 기반으로 Mission Risk 범주를 결정한다(예: Very High, High, Moderate, Low, Very Low).
  • Trust Vector를 확인하여 도메인별 신뢰 수준과 Confidence를 파악한다.
  • Recovery Feasibility에서 가장 높은 Recovery Score와 예상 회복량을 확인한다. Score가 특정 임계치(예: 0.7) 이상이면 Recovery가 실현 가능한 것으로 간주한다.
  • Policy Rule에서 허용되는 Action을 확인한다. 특정 상황에서는 일부 Action만 허용될 수 있다.
  • 위 조건을 조합하여 여섯 가지 결정 중 하나를 선택한다. 우선순위는 Continue→Continue+Monitoring→Mission Reconfiguration→Graceful Degradation→Operator Confirmation→Mission Abort 순으로 평가하되, 조건 충족 여부에 따라 건너뛴다.
  • 선택된 결정과 근거는 Mission Decision Object에 기록되고 Decision Trace Model이 생성된다.

Outputs

업데이트된 Mission Decision Object와 Decision Trace. 기존 Core Model의 Mission Decision Object는 이 구조를 반영하도록 수정된다.

Design Considerations

  • 각 결정 카테고리에 대한 정확한 임계값은 임무 유형, 위험 허용도, 법규 등을 고려하여 조직에서 정의해야 한다.
  • Operator Confirmation은 인간 오퍼레이터에게 부담을 줄 수 있으므로, 명확한 지침과 사용자 인터페이스를 제공해야 한다.
  • Graceful Degradation과 Mission Reconfiguration은 미리 계획된 임무 변경 경로가 필요하다. 임무 계획 단계에서 이러한 옵션을 설계해두어야 한다.
  • Abort 결정은 UAV와 지상 자산의 안전을 최우선으로 고려해야 하며, 보안 사고의 확산을 방지하는 조치와 함께 실행한다.
