1. Introduction

Background

본 프로젝트는 LTE/5G 기반 UAV C2(testbed) 환경에서 임무 수행을 보호하기 위한 방어 아키텍처를 설계하는 것을 목적으로 한다. 테스트베드는 다수의 eNB/UE 쌍이 공통 EPC와 APN을 공유하는 구조이며, GPS 채널은 dahnet이라는 별도 네트워크로 분리된다. 주제의 맥락에서 중요한 사실은 많은 서비스가 네트워크 상에 평문으로 노출되어 있으며, PFCP와 GTP 제어 평면에 대한 인증 부족, MongoDB 및 web API의 무인증 접근, NAS 암호 우선순위 오류, SITL serial port tcp/5762와 GPS port 14560 등 여러 오픈 포트가 존재한다는 점이다 . 이러한 환경은 임무 지향 시스템에 대해 전통적인 IDS/IPS가 단순 트래픽 패턴만으로 공격을 탐지하는 것과 달리, 임무 상의 영향과 신뢰를 함께 평가하는 방어 체계가 필요함을 보여준다.

Problem Statement

기존의 네트워크 보안 체계는 패킷 위협을 탐지하고 차단하는 데 초점을 맞추지만, UAV C2 환경에서는 다양한 계층의 구성 요소가 상호작용하면서 발생하는 복합 위협을 고려해야 한다. Kill Chain 분석에 따르면 PFCP 세션 삭제, web API 무인증 호출, MongoDB 접근, NAS null 암호 설정 등 공격은 암호화 자체의 약점이 아닌 인증·분리·키 관리 실패에서 비롯된다. 따라서 단일 지표에 기반한 탐지 시스템으로는 임무 실패에 직접적인 영향을 미치는 복합 공격을 적시에 인지하기 어렵다. 문제는 "어떤 데이터를 어떤 기준으로 평가해 임무 위험을 판단할 것인가"이며, 이를 위해 임무 맥락과 신뢰를 종합하는 설계가 요구된다.

Existing Security Limitation

테스트베드의 노출면 분석은 기존 보안 체계의 한계를 구체적으로 보여준다. 예를 들어 SITL serial port와 GPS port가 외부에 노출되어 있어 임의 명령 삽입이 가능하며, NAS null 암호 우선순위가 설정된 MME는 제어 평면이 평문으로 전송되는 상황을 유발한다. MongoDB는 인증 없이 접근 가능하고, web API도 별도의 인증 절차가 없어 공격자가 임의로 명령을 주입할 수 있다. 또한 UE 격리 기능이 비활성화되어 모든 사용자 장비가 같은 APN에 존재하므로 공격자가 타 기체의 트래픽을 관찰하거나 세션 삭제를 시도할 수 있다. 이러한 한계는 전통적인 암호화·방화벽 체계만으로는 임무의 안정성을 보장할 수 없음을 의미한다.

Why Mission‑Centric Defense

방어 아키텍처의 목표는 단순히 위협을 탐지하는 것이 아니라, 임무의 성공 여부를 중심으로 방어 결정을 내리는 것이다. 공격이 미션에 미치는 영향을 정량화하고, 임무를 지속할지 재구성할지 중단할지 판단하려면 통신 신뢰, 식별 신뢰, 세션/네트워크 신뢰, 명령 신뢰, 임무 신뢰 등 다양한 관점의 Evidence가 필요하다. 또한 임무 유형(정찰, 공격, 중계, 운송 등)에 따라 각 Capability의 중요도가 달라지므로 Mission Weight Model을 통해 신뢰 점수를 조정해야 한다. 이와 같은 Mission‑Centric Defense는 기존 IDS/IPS 대비 더 높은 가시성과 정확성을 제공하며, 실제 임무에서의 의사결정을 지원한다.

Architecture Objective

본 설계의 핵심 목표는 다음과 같다:

  • 테스트베드에서 수집 가능한 메트릭을 기반으로 12개의 공격을 흡수하는 다섯 가지 Defense Capability를 정의한다.
  • 각 Capability에서 생성된 Evidence를 정규화하고, 신뢰 계산을 위한 Trust Object를 생성한다.
  • 신뢰와 임무 맥락, 임무 가중치를 이용하여 Mission Impact를 평가할 수 있도록 구조를 마련한다.
  • 임계치·시간 창·상관분석·복구 평가 등 공통 모델을 정의하여 모든 Chapter에서 일관된 기준을 사용하도록 한다.
  • 방어 시스템의 처리 흐름을 명확히 하여, 향후 실제 방어 에이전트 설계 시 추가 데이터 모델 정의가 필요 없는 수준의 완성도를 확보한다.

Design Philosophy

아키텍처는 Capability‑Driven, Mission‑Aware를 철학으로 삼는다. 이는 12개의 공격을 각각의 탐지기로 대응하지 않고, 공통 Security Failure를 분석하여 5개의 Capability로 귀속시키는 것을 의미한다. 각 Capability는 검출된 사건을 Evidence Object로 생성하고 신뢰 점수를 산출하며, 임계치와 가중치를 사용하는 일관된 정책 하에 운영된다. 또한 임무 맥락과 우선순위를 고려해 동일한 사건이라도 상황에 따라 다른 결정을 가능케 한다. 이러한 설계 철학은 Mission‑Centric Defense가 기존 공격 중심 방어의 한계를 극복하게 한다.

Scope

본 문서는 테스트베드 상의 UAV C2 환경에 한정한다. 여기에는 EPC, eNB, UE, 각종 컨테이너, ZMQ/MAVLink 통신, PFCP/GTP 세션 관리, 웹 백엔드와 데이터베이스 등이 포함된다. GPS 채널(dahnet)과 C2/APN 채널, 코어 네트워크는 분리된 상태로 가정한다. 코드 구현, API 명세, 구체적 알고리즘은 범위에서 제외되며, 추후 세부 설계 단계에서 다룬다. 본 설계는 LTE/5G 외 다른 무선 기술에 대한 일반화를 목적으로 하지 않는다.

Assumptions

  • 테스트베드는 현실적 UAV C2 환경을 모사하며, 모든 노출면(H1–H8)과 공격 시나리오를 재현할 수 있다.
  • Capability Monitor는 필요한 메트릭(PFCP 삭제 시도, DB 접근 수, 명령 유형, NAS 암호 설정 등)을 정확히 수집할 수 있다.
  • Mission Context는 임무 계획 시스템과 연동되어 임무 유형, 단계, 우선순위 등 정보를 제공한다.
  • 시간 동기화가 이루어져 모든 Evidence에 신뢰할 수 있는 타임스탬프가 포함된다.
  • 복구 수단(예: 재시도, 통신 채널 재구성, 임무 재계획)은 사전에 정의되어 있으며, Recovery Feasibility Model에서 평가할 수 있다.

Contributions

본 설계는 다음과 같은 공헌을 한다:

  • 12개의 공격 시나리오를 분석하여 공통 Security Failure를 도출하고, 이를 방어 Capability로 일반화하였다.
  • Core Architecture Model을 통해 Evidence, Trust, Mission Context, Mission Impact, Policy, Recovery, Decision Object 등 공통 데이터 구조를 정의했다.
  • Additive Design Model을 통해 임계치 정책, 시간 창, 상관 분석, 복구 가능성, 결정 추적, 데이터 흐름, 미션 결정 모델을 추가하여 완성도를 높였다.
  • Architecture Skeleton과 Blueprint를 기반으로 구체적 Chapter 구조와 처리 흐름을 설계하였다.
  • Mission‑Centric Defense가 기존 IDS/IPS의 한계를 극복하는 방법을 제시하고, 실제 방산 환경에 적용할 수 있는 설계 지침을 제공하였다.

2. Architecture Overview

Architecture Overview

Mission‑Centric Defense Architecture는 항공기(UE)와 지상국(GCS), 그리고 코어 네트워크 사이에서 발생하는 데이터 흐름을 실시간으로 감시하고, 각 단계에서 신뢰와 임무 영향을 평가하도록 계층화된 구조를 갖는다. 전체 파이프라인은 Capability → Evidence → Trust → Mission Context → Mission Impact → Policy → Recovery → Mission Decision으로 구성되며, 각 계층은 상위 계층에 필요한 정보를 제공한다. 모든 데이터는 테스트베드에서 수집 가능한 메트릭과 로그에서 비롯되며, 임계치 및 시간 창 모델에 따라 평가된다.

Overall Pipeline

파이프라인의 주요 단계는 다음과 같다:

  • Capability Monitoring: 각 Capability Monitor가 PFCP 세션 관리, NAS 암호 설정, DB 접근, 명령 전송 등 특정 메트릭을 수집한다.
  • Evidence Generation: 모니터로부터 받은 원시 이벤트를 Evidence Object로 정규화하고 threshold policy를 적용하여 severity·weight·confidence를 부여한다.
  • Evidence Correlation: 상관 규칙을 통해 관련 Evidence를 Incident로 묶는다. 예를 들면, 5초 이내 PFCP Delete와 MAVLink Command가 발생하면 동일 Incident로 분류한다.
  • Trust Evaluation: 도메인별 Evidence 집합을 사용하여 Trust Score와 Confidence를 계산한다. Mission Weight Model을 적용해 임무 유형에 따른 가중치를 반영한다.
  • Mission Context: 임무 유형, 단계, 우선순위, 환경 제약 등을 통해 신뢰 평가를 해석한다.
  • Mission Impact: Trust 결과와 임무 가중치를 이용하여 임무 가용성, 무결성, 안전성, 연속성, 회복 가능성을 계산하고 Overall Mission Impact와 Risk를 산출한다.
  • Policy Evaluation: Mission Impact와 Rule Set을 기반으로 적절한 대응(Action)을 선택한다. 룰 우선순위, 조건, 예외 등을 포함한다.
  • Recovery Planning: 복구 후보의 실행 시간, 비용, 신뢰 회복량, 성공 확률 등을 평가하여 Recovery Score를 계산하고 우선순위를 결정한다.
  • Mission Decision: 최종적으로 Continue, Continue+Monitoring, Mission Reconfiguration, Graceful Degradation, Operator Confirmation, Mission Abort 중 하나를 선택한다.

Architecture Layers

아키텍처는 다음과 같은 레이어로 구성된다:

  • Capability Layer: 테스트베드의 각 구성 요소(eNB, MME, UPF, UE, GCS, DB, web backend 등)에 설치된 모니터가 메트릭을 수집한다. 예: PFCP Delete Attempt, Auth Failure, DB Access, MAVLink Command 등.
  • Evidence Layer: 수집된 이벤트를 Evidence Object로 변환하고, 상관 분석을 통해 Incident를 생성하며 Evidence Repository에 저장한다.
  • Trust Layer: 도메인별 Evidence를 입력으로 Trust Object를 계산한다. 신뢰 계산은 Trust Score Model과 Confidence Model을 사용하며, Mission Weight Model을 통해 임무 유형을 반영한다.
  • Mission Context Layer: 임무 유형, 단계, 우선순위, 환경 제약 등 Mission Context Object를 관리한다. Mission Context는 Trust 평가의 의미를 해석하는 역할을 한다.
  • Mission Impact Layer: Mission Impact Model을 사용하여 임무에 미치는 영향을 계산한다. 결과는 Mission Impact Object로 표현된다.
  • Policy Layer: Policy Engine은 정책 룰 집합을 적용하여 권장 Action을 결정한다. 룰은 우선순위와 조건, 예외를 포함한다.
  • Recovery Layer: Recovery Planner는 복구 후보를 평가하고 Recovery Object를 생성한다. Recovery Feasibility Model을 사용한다.
  • Decision Layer: Decision Engine은 임무 지속 여부를 판단하는 최종 계층이다. Decision Trace Model을 통해 판단 경로를 기록한다.

Component Relationships

컴포넌트 간의 관계는 생산자–소비자(Producer–Consumer) 패턴으로 정의된다. Capability Monitor는 Raw Event를 생산하며 Evidence Collector가 이를 소비한다. Correlation Engine은 Evidence를 소비하고 Incident를 생산하며, Evidence Repository는 이들을 저장한다. Trust Evaluator는 Evidence를 소비하여 신뢰를 생산하고, Mission Context Manager와 Mission Impact Evaluator는 이를 소비한다. Policy Engine과 Recovery Planner는 Mission Impact를 소비하고 대응과 복구 계획을 생성한다. 마지막으로 Decision Engine은 Policy와 Recovery 결과를 소비하여 최종 Mission Decision을 생산한다. 각 컴포넌트는 명확한 인터페이스로만 상호 연결되어 있어 계층 간 결합을 줄이고 재사용성을 높인다.

아키텍처의 인터페이스는 내부와 외부로 나뉜다. 내부 인터페이스는 위 표에 제시한 컴포넌트 간 데이터 교환을 의미하며, 객체는 명확한 스키마(Evidence Object, Trust Object 등)를 따라야 한다. 외부 인터페이스에는 다음이 포함된다:

  • Sensor Interface: Capability Monitor가 테스트베드의 컨테이너나 프로세스에서 메트릭을 수집하는 인터페이스. 예: ZMQ/MAVLink 메시지 구독, PFCP/GTP 제어 평면 모니터링, web API 호출 로그.
  • Mission Plan Interface: 임무 계획 시스템과 연동하여 Mission Context Object를 업데이트한다.
  • Operator Interface: Decision Engine이 최종 Mission Decision과 Decision Trace를 전달하여 운영자가 확인하고 필요 시 수동 개입을 할 수 있도록 한다.
  • Logging Interface: 모든 객체 생성과 평가 과정은 감사와 추적을 위해 로깅 시스템에 전송된다.

데이터는 Capability Monitor에서 시작하여 Decision Engine으로 끝나는 일련의 흐름을 따른다. Core Data Flow Model에서 정의한 바와 같이, 각 단계는 Input Object를 받아 Output Object를 생성하고 다음 단계에 전달한다. 아래 표는 주요 흐름을 요약한다.

Architecture Principles

설계는 다음 원칙에 기반한다:

  • Capability‑Driven: 공격별 탐지기가 아닌 공통 도메인을 정의하여 확장성과 유지보수성을 높인다.
  • Mission‑Aware: 임무 유형과 우선순위를 고려하여 평가하고 결정한다.
  • Data Integrity: 모든 객체는 타임스탬프와 상관 ID를 포함하여 검증 가능한 추적성을 보장한다.
  • Modularity: 각 컴포넌트는 명확한 인터페이스를 통해 상호작용하여 독립적으로 발전할 수 있다.
  • Realistic Inputs: 설계에 사용되는 메트릭과 데이터는 테스트베드에서 실제 수집 가능한 것에 한정한다.
  • Explainability: Decision Trace Model을 통해 각 결정의 근거가 투명하게 제공된다.

Deployment Concept

아키텍처는 테스트베드의 컨테이너 기반 환경에 배치된다. Capability Monitor는 각 컨테이너 내부 또는 인접 네트워크에서 동작하며, ZMQ/MAVLink 메시지를 구독하거나 PFCP, GTP, API 로그를 수집한다. Evidence, Trust 및 Mission Impact 계산은 중앙 분석 노드에서 수행되며, Policy Engine과 Recovery Planner는 임무 제어 소프트웨어와 연동되어 결정을 적용한다. 핵심 원리는 APN 채널, 코어 네트워크, GPS dahnet 간 분리된 네트워크를 유지하면서 모니터가 모든 중요한 포인트를 관찰하도록 배치하는 것이다.

3. Threat Analysis

Threat Landscape

UAV C2 테스트베드에서 발생할 수 있는 위협은 네트워크, 인증, 세션 관리, 명령 및 임무 계층에 걸쳐 있다. 공격 시나리오 분석과 노출면 테이블에 따르면, 암호화 알고리즘은 안전하게 구현되었지만, 제어 평면과 애플리케이션 계층에서 인증과 분리 실패가 주요 취약점이다. 예를 들어 PFCP 세션 삭제 공격은 제어 평면에 대한 인증 부재를 악용하며, web API와 MongoDB에 대한 무인증 접근은 명령 주입과 데이터 변조를 가능하게 한다. 또한 동일 APN 내에서 UE 격리가 이루어지지 않아 한 기체의 트래픽이 다른 기체에 영향을 미칠 수 있다.

Threat Classification

공격을 단일 이벤트로 나열하는 대신, 공통적인 Security Failure를 기준으로 다음과 같이 분류한다:

  • Authentication & Authorization Failures: web API, MongoDB, PFCP/GTP control plane의 인증 부재로 인한 무단 접근 및 명령 주입.
  • Network Segmentation Failures: UE 격리 미비로 인해 동일 APN에 존재하는 다른 기체의 세션을 중단하거나 트래픽을 관찰할 수 있음.
  • Session Integrity Failures: PFCP Delete, Session Reset 메시지를 통한 세션 취소 및 끊김 유발.
  • Key Management & Encryption Failures: NAS null 암호 우선순위, 키 배포의 부적절함으로 인해 기밀성과 무결성이 위협받음.
  • Command Integrity Failures: MAVLink Command의 무결성 검증 부족과 명령 서명 키 노출로 발생하는 명령 변조.
  • Infrastructure Exposure: SITL serial port 5762, GPS port 14560, API port 8080 등 오픈 포트로 인한 외부 공격 접점.

Attack Scenario Analysis

12개의 공격 시나리오를 자세히 분석한 결과, 대부분의 공격은 위에서 정의한 분류에 속한다. 예를 들어 PFCP Delete와 세션 재설정 공격(T x – S3)은 Session Integrity Failure에 해당하며, Oracle DB Injection과 web API Exploit은 Authentication & Authorization Failure에 해당한다. NAS null 암호 설정과 키 배포 문제는 Key Management Failure로 분류된다. MAVLink Replay 및 Command Injection은 Command Integrity Failure에 속한다. 이러한 분류는 각 공격을 개별 탐지기로 대응하는 대신, 공유된 실패 원인을 기반으로 Capability를 설계해야 함을 강조한다.

Common Security Failures

모든 시나리오를 종합하면 다음과 같은 공통 보안 실패가 도출된다:

  • Unverified Control Plane: PFCP 및 NAS 제어 평면에서 암호화 및 인증이 부재하여 세션 관리가 공격자가 변조할 수 있는 상태이다.
  • Plaintext Application Interfaces: web API와 MongoDB가 인증 없이 노출되어 있어 쉽게 침해된다.
  • Poor Key Management: 서명 키가 공개적으로 배포되거나 재사용되어 명령 위변조가 가능하다.
  • No Isolation: UE 격리가 미비하여 공통 APN에서 공격 전파가 쉽다.
  • Lack of Monitoring & Thresholding: 현재 시스템은 지표를 수집하지만 정량적 평가나 임계치가 없어 이벤트의 심각도를 구분할 수 없다.

Need for Defense Capabilities

위의 보안 실패는 다섯 가지 Capability의 필요성을 직접적으로 보여준다:

  • Communication Trust Capability: PFCP/GTP 제어 평면과 NAS 암호 설정을 모니터링하여 통신 채널의 신뢰를 평가한다. 패킷 손실, RTT, 삭제 시도 등 메트릭을 수집한다.
  • Identity & Access Trust Capability: web API, DB, MME 등에서 발생하는 인증 이벤트를 평가하여 무단 접근을 탐지하고 사용자 신원을 검증한다.
  • Session & Network Trust Capability: PFCP Delete, Session Reset, UE isolation 상태를 모니터링하여 세션 및 네트워크 분리의 무결성을 확보한다.
  • Command Trust Capability: MAVLink Command의 무결성 검증, 서명 확인, 명령 유형과 시퀀스 분석을 통해 명령의 적법성을 평가한다.
  • Mission Trust Capability: 임무 단계, 우선순위, 환경 제약을 모니터링하고 임무 중 나타나는 이상 행동을 평가한다.

Threat Surface

테스트베드에서 확인된 노출면은 아래와 같다:

  • SITL Serial Port (tcp/5762): 원격에서 컨트롤 가능한 시리얼 포트. 명령 재주입 위험.
  • PFCP Control Plane: 인증되지 않은 PFCP Session Delete 및 Create 메시지.
  • Web API (8080) & MongoDB (14556): 인증 없이 접근 가능해 데이터 탈취와 명령 삽입 가능.
  • NAS Null Encryption: EEA0 우선순위가 설정된 MME로 인해 제어 평면이 평문으로 전송.
  • Key Distribution: 명령 서명 키가 노출되어 있는 상태.
  • UE Isolation: 동일 APN에 여러 기체가 존재하여 세션 간 간섭 가능.
  • GPS Port (14560): GPS dahnet 포트가 외부에 노출되어 GPS 스푸핑 가능.

Attack → Capability Mapping

모든 공격 시나리오를 Capability로 매핑하면 다음과 같은 패턴이 나타난다. PFCP Delete, Session Reset, UE Isolation 공격은 Session & Network Trust Capability에 의해 처리된다. NAS Null Cipher, 키 유출, SITL port exposure, GPS spoofing은 Communication Trust Capability가 담당한다. DB Injection, Web API Exploit, 인증 우회는 Identity & Access Trust Capability에 대응하며, MAVLink Replay와 Command Injection은 Command Trust Capability가 처리한다. Mission Trust Capability는 임무 단계와 우선순위를 평가해, 동일 공격에 대해서도 임무 중요도에 따라 다른 대응 수준을 허용한다. 이 매핑을 통해 12개의 공격을 다섯 개의 Capability에 통합하여, 방어 시스템을 단순화하고 확장 가능하게 한다.

4. Defense Capability Architecture

Overview

이 장에서는 다섯 가지 Defense Capability의 구조를 설계한다. 각 Capability는 특정 도메인의 자산을 보호하며, 입력 메트릭을 평가하여 Evidence와 Trust를 생성한다. 아래에서 각 Capability의 구성과 데이터 흐름을 구체적으로 설명한다. 설계는 Core Architecture Model과 Additive Design Model의 데이터 구조를 활용하고, 테스트베드에서 실제로 수집 가능한 메트릭만을 사용한다.

4.1 Communication Trust Capability

Purpose

통신 채널의 가용성과 무결성을 유지하기 위해 PFCP/GTP 제어 평면, NAS 암호 설정, 패킷 손실과 RTT 등을 모니터링하여 신뢰를 평가한다.

Protected Assets

통신 링크와 세션(UE–eNB–UPF–GCS 경로), 제어 평면 메시지(PFCP Create/Delete, NAS Security Mode), GPS 데이터 채널.

Input Metrics

  • PFCP_Delete_Attempt: 0이어야 정상. 1 건 이상이면 경고, 반복 시 위험.
  • PFCP_Create_Attempt/Session_Reset: 정상 세션 생성 비율 대비 비정상 증가 여부.
  • NAS_Cipher_Order: EEA2 우선순위인지 여부; EEA0이면 위험.
  • Packet_Loss (%): 통신 경로의 손실률; Mission Weight Model에 따라 임계치가 달라진다.
  • RTT (ms): 왕복 시간; 일정 기간 상승하면 DoS 의심.
  • Port_State: SITL serial port 5762, GPS port 14560의 개방 여부.

Input Objects

Raw Events: PFCP 로그, NAS Security Mode Command, TCP/UDP 포트 스캔, SNMP/metrics 수집 결과.

Processing Responsibility

Evidence Collector는 Input Metrics를 받아 Threshold Policy Model과 Time Window Model을 적용하여 severity와 confidence를 계산한다. Correlation Engine은 PFCP Delete와 포트 스캔이 단기간에 함께 발생하면 동일 Incident로 묶는다. Trust Evaluator는 Evidence를 통합하여 Communication Trust Score를 계산한다.

Generated Evidence

각 이벤트는 Evidence Object로 저장되며, 필드에는 metric, observed_value, expected_value, threshold, severity, weight, confidence, timestamp, ttl, correlation_id 등이 포함된다.

Generated Trust

Trust Object(domain=communication)는 0–100 범위의 신뢰 점수와 confidence를 포함한다. Severity와 weight, Time Window 평균을 고려하여 계산한다.

Generated Output

Communication Trust Capability는 계산된 Trust Object를 Trust Layer에 전달하며, Mission Impact 평가에서 가용성과 통신 연속성 항목에 영향을 준다.

Interfaces

  • Upstream: Capability Monitor로부터 Raw Events를 수신.
  • Downstream: Evidence Collector와 Trust Evaluator에 Evidence Object 및 Trust Object를 전달.
  • External: Monitoring Dashboard에 통신 상태를 제공하여 운영자가 확인할 수 있다.

Related Threats

PFCP 세션 삭제, NAS null 암호 설정, 키 유출, 포트 오픈으로 인한 공격 등 모든 Communication 관련 위협.

Related Attack Scenarios

PFCP DoS, NAS Null Cipher, GPS Spoofing, SITL Port Injection, Key Distribution Attack 등.

Mission Contribution

통신 채널의 가용성 확보는 모든 임무에서 필수적이며, Communication Trust Score는 Mission Impact의 가용성, 연속성 항목에 큰 비중으로 반영된다.

Architecture Position

Capability Layer에 위치하며 Evidence Layer와 Trust Layer 사이에 직접 연결된다.

Capability Flow

PFCP/NAS/GPS Metrics → Evidence Collector → Evidence Object(s) → Trust Evaluator → Communication Trust Object

Failure Handling

모니터가 비정상적인 패턴을 감지하지 못하거나 통신 로그가 손실될 경우, Confidence가 낮게 설정되고, 신뢰 계산에서 페널티를 적용한다. 센서 손실이 지속되면 보조 채널(예: GTP 통계)로 대체한다.

Design Considerations

메트릭의 정상 범위는 테스트베드 실측 데이터를 기반으로 정하며, 임무 유형에 따라 가중치를 조정한다. GPS 채널은 별도 네트워크로 분리되어 있어 통신 trust와 별도로 평가될 수 있다.

4.2 Identity & Access Trust Capability

Purpose

사용자와 서비스의 신원을 검증하고 접근 권한을 평가하여 무단 접근과 인증 우회를 방지한다.

Protected Assets

web backend, MongoDB 데이터베이스, PFCP/GTP 제어 평면, Mission Control API.

Input Metrics

  • Auth_Failure: 로그인 실패 횟수 및 패턴.
  • DB_Access: MongoDB 접속 시도 횟수 및 성공/실패 여부.
  • API_Call_Count: 인증 없이 호출된 web API 요청 수.
  • Credential_Verification: 전자 서명 검증 결과.
  • Session_Token_Usage: 만료 또는 이상 사용 패턴.

Input Objects

Authentication 로그, web server 로그, database audit 로그, token validation 결과.

Processing Responsibility

Evidence Collector는 로그인 실패가 일정 기간 동안 급증하는지 체크하고, 무인증 API 호출 여부를 평가한다. Correlation Engine은 동일 Source IP가 여러 서비스에 접근하는지 상관 분석한다. Trust Evaluator는 인증 성공률과 실패 패턴을 이용하여 Identity & Access Trust Score를 계산한다.

Generated Evidence

Evidence Object는 metric=Auth_Failure, DB_Access, API_Call_Count 등으로 생성된다. severity는 Threshold Policy Model에 따라 정의된다.

Generated Trust

Identity & Access Trust Object는 인증 관련 신뢰 점수와 confidence를 포함한다. 신뢰 점수가 낮을수록 무단 접근 가능성이 높다.

Generated Output

산출된 Trust Object는 Mission Impact 평가에서 무결성, 안전성 항목에 영향을 준다.

Interfaces

  • Upstream: AAA 서버, OAuth/Token 서비스로부터 로그 수신.
  • Downstream: Evidence Collector, Trust Evaluator.
  • External: Identity & Access Management 시스템과 연동하여 계정 상태를 업데이트.

Related Threats

Oracle Injection, web API exploit, MongoDB unauthenticated access, session hijacking.

Related Attack Scenarios

TM1/V1 Oracle Injection, NF‑4 web API exploit, NF‑3 MongoDB attack 등.

Mission Contribution

신원과 접근의 신뢰는 임무의 무결성을 보호하며, 높은 우선순위 임무에서는 인증 실패가 즉각적인 위험으로 간주된다.

Architecture Position

Capability Layer에 위치하며 Evidence Layer와 Trust Layer를 거쳐 Mission Impact로 전달된다.

Capability Flow

Auth/DB/API Logs → Evidence Collector → Evidence Object(s) → Trust Evaluator → Identity & Access Trust Object

Failure Handling

로그 누락이나 인증 시스템 장애 시 confidence가 낮아지며, 보수적(낮은 신뢰) 평가가 적용된다. 모니터링 에이전트는 대체 로그 경로를 사용해 지속성을 확보한다.

Design Considerations

명령 주입과 DB 공격은 단일 이벤트라도 치명적 결과를 유발할 수 있으므로 Threshold Policy Model에서 낮은 임계치를 적용한다.

4.3 Session & Network Trust Capability

Purpose

세션 상태와 네트워크 분리의 무결성을 보장하기 위해 PFCP, GTP 세션과 APN 격리 현황을 모니터링한다.

Protected Assets

UE–eNB–UPF 사이의 데이터 및 제어 세션, APN 구성, UE MAC/IMSI 매핑.

Input Metrics

  • PFCP_Delete_Attempt: 세션 삭제 시도 횟수.
  • Session_Reset_Count: GTP Session 재설정 횟수.
  • UE_Isolation_State: UE 격리 설정 상태(Enabled/Disabled).
  • APN_Flow_Entropy: 동일 APN 내 트래픽 분포 변화.
  • Session_TTL: 세션의 TTL 값 변화. 비정상적으로 짧아지면 공격 의심.

Input Objects

UPF/MGW 로그, PFCP statistics, GTP tunnel state, APN configuration state.

Processing Responsibility

Evidence Collector는 PFCP 삭제와 세션 재설정 이벤트를 수집하고, UE Isolation State를 주기적으로 확인한다. Correlation Engine은 PFCP Delete 후 특정 APN 트래픽이 줄어든 경우를 동일 Incident로 묶는다. Trust Evaluator는 세션 유지 여부와 격리 상태를 평가하여 Session & Network Trust Score를 계산한다.

Generated Evidence

metric =PFCP_Delete_Attempt, Session_Reset_Count, UE_Isolation_State 등으로 Evidence Object를 생성한다.

Generated Trust

Session & Network Trust Object는 세션 무결성 신뢰 점수와 confidence를 제공하며, 낮은 신뢰는 임무 가용성 감소로 이어진다.

Generated Output

Trust Object는 Mission Impact 평가에서 가용성 및 연속성에 반영된다.

Interfaces

  • Upstream: PFCP/GTP 로깅 시스템, network monitor.
  • Downstream: Evidence Layer, Trust Layer.

Related Threats

PFCP Delete 공격, Session Reset Flooding, UE Isolation disabled 공격.

Related Attack Scenarios

TM2 PFCP Session Deletion, NF‑6 Session Reset Exploit, NF‑7 UE Isolation Attack 등.

Mission Contribution

세션과 네트워크 안정성은 통신 가용성을 직접 결정하므로, 높은 가중치를 가진다.

Architecture Position

Capability Layer – Evidence Layer – Trust Layer로 이어지는 구조.

Capability Flow

PFCP/GTP/APN Metrics → Evidence Collector → Evidence Object(s) → Trust Evaluator → Session & Network Trust Object

Failure Handling

UE Isolation 상태를 확인하는 모듈이 실패하면 APN 트래픽 엔트로피 지표를 대신 사용한다. 로그 손실 시 Confidence 감소를 통해 보수적 평가를 수행한다.

Design Considerations

APN 격리 기능은 테스트베드에서 설정 가능한지 확인해야 하며, 현장에서 지원되지 않는 경우 다른 메트릭으로 대체해야 한다.

4.4 Command Trust Capability

Purpose

무인기의 제어 명령이 적법하며 변조되지 않았는지 확인한다. 특히 MAVLink 2.0 메시지 서명 및 명령의 종류, 시퀀스를 검증한다.

Protected Assets

무인기 비행 제어 권한, GCS → UE 명령 채널, 비행 계획.

Input Metrics

  • Command_Type: LAND, ARM, TAKEOFF, WAYPOINT 등.
  • Signature_Verified: 명령 서명의 유효성 여부.
  • Sequence_Number: 명령 시퀀스 점프나 재생 여부.
  • Command_Source: 명령을 발신한 IP/ID.
  • Unauthorized_Command: 승인되지 않은 명령 유형.

Input Objects

MAVLink 메시지 로그, 명령 서명 검증 결과, GCS 및 UE ID 매핑 정보.

Processing Responsibility

Evidence Collector는 각 명령에 대해 서명 검증, 명령 타입, 시퀀스 번호를 기록한다. Correlation Engine은 동일 Source가 짧은 시간에 반복적으로 동일 명령을 전송하는 경우를 Incident로 묶는다. Trust Evaluator는 미승인 명령과 서명 실패 비율을 기반으로 Command Trust Score를 계산한다.

Generated Evidence

metric =Unauthorized_Command, Signature_Verified, Sequence_Anomaly, Command_Source 등으로 Evidence를 생성한다.

Generated Trust

Command Trust Object는 명령 채널의 신뢰 수준을 나타낸다. 신뢰가 낮으면 Mission Impact 평가에서 안전성과 무결성 항목에 영향을 준다.

Generated Output

Trust Object는 Trust Layer를 통해 Mission Impact에 전달되며, Policy Engine이 적절한 방어 조치를 결정하는 데 사용된다.

Interfaces

  • Upstream: MAVLink Proxy, Command Logger.
  • Downstream: Evidence Collector, Trust Evaluator.

Related Threats

MAVLink Replay, Unauthorized Command, Command Tampering.

Related Attack Scenarios

V1 Replay Attack, NF‑4 Command Injection, Signature Bypass 등.

Mission Contribution

명령 신뢰는 임무의 무결성과 안전성을 직접적으로 결정한다. 비행제어 명령이 변조될 경우 임무가 즉시 실패할 수 있다.

Architecture Position

Capability Layer에서 Command Monitor가 동작하며, Evidence와 Trust를 상위 계층으로 전달한다.

Capability Flow

MAVLink Commands → Evidence Collector → Evidence Object(s) → Trust Evaluator → Command Trust Object

Failure Handling

명령 서명 검증 모듈이 실패할 경우, 신뢰 점수를 즉각적으로 낮추고 Policy Engine에 알림을 보낸다. 또한 가짜 명령은 Block List에 등록한다.

Design Considerations

Command Trust는 비행 제어 안전과 직결되므로 Threshold Policy Model에서 매우 낮은 임계치를 설정한다.

4.5 Mission Trust Capability

Purpose

임무 실행 환경과 상태를 모니터링하여 임무에 대한 신뢰를 평가한다. 임무 유형, 단계, 목표와 환경 변수의 일관성을 확인한다.

Protected Assets

임무 계획, 우선순위, 임무 수행을 위한 자원(연료, 시간), 중요 자산(UAV 상태, 페이로드).

Input Metrics

  • Mission_Type: Recon, Strike, Relay, Transport, Monitoring 등.
  • Mission_Phase: Planning, Takeoff, Transit, Operation, Return, Landing.
  • Mission_Priority: High, Medium, Low 등.
  • Mission_Goal_Status: 목표 달성률 또는 과업 완료 여부.
  • Operational_Constraint: 비행 금지 구역, 시간 제한, 연료/배터리 상태.

Input Objects

Mission Plan 파일, UAV 상태 보고, 환경 센서 데이터, 정책 데이터베이스.

Processing Responsibility

Mission Context Manager는 임무 계획에서 Mission Context Object를 생성한다. Evidence Collector와 Trust Evaluator로부터 받은 정보와 Mission Context를 비교하여 임무에서 예상치 못한 변칙을 탐지한다. Trust Evaluator는 Mission 도메인에 대한 신뢰를 계산한다.

Generated Evidence

Mission Trust Capability는 직접 Evidence를 생성하지 않지만, Mission Context와 Trust 결과를 이용해 Mission Impact를 계산한다.

Generated Trust

Mission Trust Object는 Mission Context와 다른 도메인 신뢰 점수를 종합하여 Mission Level 신뢰를 제공한다.

Generated Output

Mission Trust Object는 Mission Impact Layer로 전달되어 Overall Mission Impact를 계산하는 데 사용된다.

Interfaces

  • Upstream: Mission Plan System, UAV Telemetry.
  • Downstream: Mission Impact Evaluator.

Related Threats

Mission Hijacking, Mission Policy Violation.

Related Attack Scenarios

NF‑5 Mission Reassignment Attack 등.

Mission Contribution

임무 신뢰는 임무의 성공과 직접적으로 연결되어 있으며, 모든 도메인의 신뢰를 종합한 전반적 신뢰의 최종 단계이다.

Architecture Position

Mission Context Layer와 Trust Layer 사이에서 동작한다.

Capability Flow

Mission Context Inputs → Mission Context Manager → Mission Trust Object → Mission Impact Evaluation

Failure Handling

Mission 계획 데이터가 없는 경우, 임무를 기본(low) 신뢰 상태로 평가한다. Mission Phase 오류나 우선순위 불일치가 발견되면 Policy Engine에 경보를 전달한다.

Design Considerations

Mission Trust Capability는 다른 도메인과 달리 직접 Evidence를 생성하지 않으므로, 신뢰 계산이 다른 도메인의 신뢰에 크게 의존한다. Mission Weight Model을 통해 각 Capability의 영향도를 조절한다.

5. Evidence Architecture

Overview

Evidence는 방어 아키텍처에서 가장 중요한 객체이다. 모든 판단과 신뢰 계산, 정책 적용은 Evidence에 기반한다. 본 장은 Evidence의 생성, 상관, 저장, 품질 관리, 수명 주기와 인터페이스를 구체적으로 설계한다.

Evidence Sources

Evidence는 Capability Monitor가 수집한 Raw Metrics에서 만들어진다. 예를 들어 PFCP Delete, NAS_Cipher_Order, Auth_Failure, DB_Access, Command_Type, Mission_Phase 등이 이에 해당한다. 모든 메트릭은 Testbed에서 실시간으로 측정 가능해야 하며, Threshold Policy Model과 연계된다.

Evidence Collection

Evidence Collector는 Sensor Interface를 통해 Raw Metrics를 수신하고, Metric 정의에 따라 값을 검증한다. Threshold Policy Model을 적용하여 Normal/Warning/Critical/Danger 구간을 구분하고 severity와 weight를 계산한다. Time Window Model을 활용해 현재 상태와 롤링 윈도우 평균을 비교한다.

Evidence Normalization

서로 다른 형식의 Raw Metrics를 일관된 구조로 변환하기 위해 Evidence Object 스키마를 사용한다. 각 Evidence는 고유 ID, Capability, Source, Entity, Metric, Observed Value, Expected Value, Threshold, Severity, Weight, Confidence, Timestamp, TTL, Correlation ID, Description을 포함한다. 이러한 구조는 추후 Trust Evaluation 단계에서 자동으로 처리될 수 있도록 표준화되어 있다.

Evidence Correlation

상관 분석은 개별 Evidence를 Incident로 묶어 의미 있는 사건을 구성한다. Correlation Rules는 Additive Design Model에서 정의되며, 시간 창, 동일 Source/Target, Capability 조합 등을 기준으로 Incident를 생성한다. Correlation Score는 Incident의 심각도를 나타내며, 여러 Evidence의 severity·confidence 값을 종합하여 계산한다.

Incident Generation

Correlation Engine은 Correlation Rules에 따라 Incident Object를 생성한다. Incident에는 Incident_ID, Evidence_List, Correlation_Score, Start_Time, End_Time, Affected_Entities, Description이 포함된다. Incident는 Trust Evaluation과 Mission Impact 평가에 중요한 단위를 제공한다.

Evidence Repository

Evidence Repository는 Evidence Objects와 Incident Records를 저장하는 중앙 저장소이다. 인덱스는 Evidence_ID, Correlation_ID, Timestamp, Capability 등으로 구성되어 빠른 조회를 지원한다. TTL 필드를 통해 만료된 Evidence는 자동으로 삭제된다.

Evidence Quality

Evidence 품질은 채널 신뢰성, 데이터 완전성, 정확성에 따라 평가된다. Sensor 오류, 로그 누락 등은 낮은 quality로 표시되며, Confidence Model은 이를 고려하여 final confidence를 계산한다.

Evidence Confidence

Confidence는 Evidence의 신뢰도를 0–1 범위로 표현한다. Additive Design Model에서 정의한 요소(증거 수, 품질, 상관 관계, 시간 경과, conflict 여부)에 따라 계산하며, Trust Score 계산에서 weighting factor로 사용된다.

Evidence Lifecycle

Evidence는 수집 → 정규화 → 상관 → 저장 → 만료 순으로 흐른다. 만료되기 전에 재평가가 필요한 경우 TTL을 연장할 수 있다. Incident는 관련 Evidence가 만료되면 종료된다.

Evidence Flow Diagram

Raw Metrics → Evidence Collector → Evidence Normalization → Evidence Object → Correlation Engine
       → Incident Object → Evidence Repository → Trust Evaluator

Evidence Output

Evidence Object와 Incident Object는 Trust Evaluator와 Policy Engine에서 소비된다. 또한 Decision Trace Model에 기록되어 추후 감사에 활용된다.

Evidence Interface

Evidence Layer는 다음 인터페이스를 제공한다:

  • StoreEvidence(Evidence Object): Evidence Repository에 Evidence를 저장한다.
  • QueryEvidence(query): 특정 조건(시간, Capability, Severity 등)으로 Evidence를 조회한다.
  • StoreIncident(Incident Object): Incident를 저장한다.
  • SubscribeIncident(domain): 특정 도메인 Incident 알림을 구독한다.

Evidence Traceability

Evidence_ID와 Correlation_ID는 Decision Trace Model과 연계되어 최종 Mission Decision에 어떤 증거가 사용되었는지 확인할 수 있게 한다. 로그 시스템은 Evidence 생성부터 Decision에 이르기까지 모든 단계를 기록한다.

Evidence Storage Policy

Evidence와 Incident는 법적 요구 사항 및 임무 기밀성에 따라 저장 기간이 결정된다. 민감한 데이터는 암호화하고, 저장소 접근은 Identity & Access Capability의 통제를 받는다. 데이터 보존 정책은 정책 룰로 관리되며, 만료 후 즉시 파기한다.

6. Trust Architecture

Purpose

Trust Architecture의 목적은 다양한 Capability에서 생성된 Evidence와 Incident 데이터를 기반으로 각 신뢰 도메인에 대한 신뢰 점수를 산출하고, 이를 Mission Context Layer와 Mission Impact Layer로 전달하는 것이다. 신뢰는 임무가 안전하게 지속될 수 있는지를 판단하는 핵심 척도이며, 통신, 식별, 세션/네트워크, 명령, 임무의 각 도메인별로 평가된다.

Why Trust Layer is Required

테스트베드에서는 PFCP 세션 삭제, web API 무인증 접근, MongoDB 접근, NAS null 암호 설정 등 다양한 공격이 발생할 수 있다. 이러한 공격은 암호화 내부의 취약점이 아닌 인증과 분리 실패에서 비롯되며, 단일 지표로는 임무에 미치는 영향을 예측하기 어렵다. Trust Layer는 각 Evidence를 Mission Weight Model과 Threshold Policy에 따라 가중치화하고, Confidence를 반영하여 정량적 신뢰 점수를 제공함으로써 임무 위험을 판단하는 기초를 제공한다.

Architecture Overview

Trust Architecture는 Evidence Object와 Incident Object를 입력으로 받아, 도메인별로 필터링하고, 집계(Aggregation)하고, Mission Weight와 Threshold Policy를 이용해 가중치를 적용한다. 이후 Confidence를 반영하여 0~100 범위의 신뢰 점수를 계산한 후 Trust Object를 생성한다. 최종적으로 도메인별 Trust Object와 전체적인 신뢰 벡터를 Mission Context Layer로 전달한다.

Trust Domains

신뢰는 다섯 개의 도메인으로 구분된다.

  • Communication Trust: PFCP/GTP 제어 평면, ZMQ/MAVLink 통신 상태, 패킷 손실, RTT 등 통신 신뢰도를 평가한다.
  • Identity & Access Trust: UE 인증 상태, NAS 암호 우선순위, Web API 인증, MongoDB 접근 등 식별과 접근 제어의 신뢰를 평가한다.
  • Session & Network Trust: PFCP Delete Attempt, Session Reset, UE 격리, 네트워크 분리 등 세션과 네트워크 계층의 무결성을 평가한다.
  • Command Trust: MAVLink Command, 무인증 명령 삽입, 토픽 변조 등 명령 계층의 신뢰를 평가한다.
  • Mission Trust: GPS port 14560 변조, 임무 컨텍스트 데이터 변조 등 임무 자체에 대한 신뢰를 평가한다.

Trust Input Objects

Trust Layer는 다음 객체를 입력으로 사용한다:

  • Evidence Object: 각 Capability에서 생성되는 Evidence는 metric, observed_value, expected_value, severity, weight, confidence 등을 포함한다.
  • Incident Object: Evidence Correlation Model에서 생성된 Incident는 여러 Evidence를 하나의 사건으로 묶은 객체이며, correlation_rule과 correlation_score를 포함한다.
  • Mission Weight: Mission Weight Model에서 정의된 도메인별 가중치 벡터.
  • Threshold Policy: Metric별 Normal/Warning/Critical/Danger 범위와 severity factor를 포함하는 표.
  • Confidence: Evidence Object와 Incident Object에 계산된 confidence 값. Confidence는 증거 수, 품질, 상관관계, 시간 경과 등 요인을 포함한다.

Trust Processing Pipeline

Trust Architecture의 처리 흐름은 다음과 같다:

  1. Filtering: Evidence Repository에서 Observation Window 내의 Evidence를 도메인에 맞추어 선택한다. TTL이 지나거나 Mission Context와 관련 없는 Evidence는 제외한다.
  2. Aggregation: 선택된 Evidence들을 동일한 metric 또는 incident 기준으로 그룹화하여 전체 severity를 계산한다. 동일한 Incident에 속한 Evidence는 Incident Object의 correlation_score를 사용해 가중합한다.
  3. Weighting: 각 Evidence의 severity에 Mission Weight Model에서 정의한 도메인별 weight를 곱한다. 예를 들어 정찰 임무에서는 Communication Trust에 높은 weight가, 공격 임무에서는 Command Trust에 높은 weight가 적용된다.
  4. Confidence Reflection: Aggregation 결과에 Evidence와 Incident의 confidence를 적용하여 신뢰 점수에 대한 조정 계수를 구한다. Confidence가 낮을수록 신뢰 점수는 보수적으로 감소한다.
  5. Trust Score: 가중치와 confidence를 적용한 severity 값을 Trust Score Model에 입력하여 0~100 사이의 신뢰 점수로 변환한다. severity가 높을수록, weight가 클수록 신뢰 점수는 낮아진다.
  6. Trust Object Generation: 각 도메인별로 Trust Object를 생성한다. 이 객체는 domain, trust_score, confidence, evidence_count, supporting_evidence, conflicting_evidence, calculation_result, reason 등을 포함한다.

Trust Score Model

Trust Score Model은 severity와 weight의 합을 0~100 범위로 매핑한다. 아래 표는 신뢰 점수 구간과 의미를 정의한다.

Trust RangeMeaning
100–90Very High: 모든 증거가 정상 범위이며, 임무에 대한 위협이 거의 없음. 통신·식별·세션·명령·임무 도메인 모두 안전.
89–70High: 약간의 경고 수준 Evidence가 존재하지만, 통신과 세션의 기본 무결성이 유지됨. 정찰 임무나 일반 운송에 큰 지장 없음.
69–50Moderate: 중요한 메트릭에서 Warning 또는 Critical 수준의 Evidence가 존재하여 잠재적 위험이 높아짐. 임무 재구성 또는 감시 강화가 필요.
49–30Low: 여러 Critical Evidence가 동시에 발생하거나 Danger 수준의 Evidence가 확인됨. 임무에 심각한 위협이 존재하며, 재구성 또는 연쇄 복구가 요구됨.
29–0Very Low: 신뢰할 수 없는 상태이며, 지속적인 공격 또는 명령 변조가 발견됨. 임무 중단이나 긴급 복구가 필요하다.

Confidence Reflection

Confidence는 신뢰 점수 계산에서 조정 계수로 사용된다. 예를 들어 신뢰 점수 계산식이 Adjusted Trust = BaseTrust × Confidence라고 할 때, Confidence 값이 0.8이면 신뢰 점수는 20% 감소한다. Evidence가 많고 품질이 높으며 시간적으로 가까울수록 confidence가 증가하고, 상관 규칙이 충돌하거나 오래된 Evidence일수록 confidence가 감소한다.

Trust Output

Trust Layer의 출력은 다음과 같다:

  • Trust Object: 도메인별 신뢰 결과를 포함하는 객체. 각 객체는 domain, trust_score, confidence, evidence_count, supporting_evidence, conflicting_evidence, calculation_result, reason 등 필드를 가진다.
  • Trust Vector: 모든 도메인의 trust_score를 순서대로 나열한 배열. 예: [Comm: 85, Id: 90, Session: 70, Command: 65, Mission: 75].
  • Trust Summary: Trust Vector에 기반하여 전체적인 임무 신뢰 수준과 위험 메시지를 요약한 보고서.

Trust Interface

Trust Layer는 Mission Context & Mission Impact Layer에 다음 정보를 전달한다:

  • Trust Vector (도메인별 신뢰 점수)
  • Confidence (종합 confidence 값)
  • Supporting Evidence List (Trust Object가 의존하는 Evidence 목록)
  • Trust Summary (전반적 위험 수준 및 설명)

Trust Failure Handling

다음과 같은 상황에 대한 실패 처리 방안을 정의한다:

  • Evidence Scarcity: Observation Window 내에 Evidence가 부족하면 직전 신뢰 점수를 유지하되 confidence를 감소시켜 Mission Context가 보수적으로 해석하도록 한다.
  • Conflicting Evidence: 동일 도메인에서 Supporting Evidence와 Conflicting Evidence가 동시에 존재하면 correlation_score와 confidence를 사용하여 우세 증거를 선택한다.
  • Invalid Mission Weight: Mission Weight가 존재하지 않거나 합이 100이 아닌 경우 기본 weight (균등 분배)를 사용하고, Mission Context Layer에 경고를 전달한다.

Design Constraints

Trust Architecture 설계 시 고려해야 할 제약 사항:

  • 신뢰 점수는 0에서 100 사이로 정규화되어야 하며, 모든 도메인에서 동일한 척도를 사용한다.
  • Mission Weight와 Threshold Policy는 테스트베드와 임무 유형에 따라 동적으로 업데이트될 수 있으나, 신뢰 계산 시점에는 고정된 값이어야 한다.
  • Trust Layer는 이전 계층에서 정의된 데이터 모델을 변경하지 않고, Evidence Object 및 Incident Object를 읽기 전용으로 사용한다.
  • 시간 창(Time Window Model)과 임계치(Threshold Policy Model)를 일관되게 준수해야 한다.

Summary

Trust Architecture는 다양한 도메인의 Evidence를 Mission Weight, Threshold Policy, Confidence와 결합하여 신뢰 점수를 산출한다. 이 과정은 Filtering→Aggregation→Weighting→Confidence Reflection→Trust Score→Trust Object라는 파이프라인으로 구성되어 있으며, 결과물은 Mission Context Layer에 전달된다. 신뢰 점수는 임무 위험을 정량화하는 데 사용되며, 낮은 신뢰는 Mission Impact Layer와 Policy Layer에서 즉각적인 대응을 필요로 한다.

7. Mission Context & Mission Impact Architecture

Purpose

Mission Context & Mission Impact Architecture의 목적은 Trust Layer에서 계산된 신뢰 점수를 임무 맥락에 따라 해석하고, 임무 성공에 대한 영향을 정량화하는 것이다. Mission Context Object는 임무의 유형과 목표, 우선순위, 환경 제약을 정의하며, Mission Impact Model은 신뢰와 Mission Weight를 기반으로 임무 가용성, 무결성, 안전, 연속성, 회복 가능성, 위험을 평가한다.

Mission Context Object

Mission Context Object는 임무의 본질을 표현하는 구조체로 다음 필드를 포함한다:

FieldDescription
mission_type임무 유형 (예: Recon, Strike, Relay, Transport, Monitoring). 임무 유형에 따라 Mission Weight가 달라진다.
mission_phase임무의 현재 단계 (예: Launch, Transit, Operation, Return).
mission_priority임무의 중요도 (High/Medium/Low). Critical Asset과 연계되어 Mission Impact를 계산할 때 사용된다.
mission_goal임무의 목표 (예: 특정 좌표로 정보 수집, 타깃 제거, 물자 운송 등).
critical_asset임무 수행에 필수적인 자산 (예: 통신 링크, 연료, 페이로드).
operational_constraint비행 금지 구역, 시간 제한, 통신 금지 구역 등 제약사항.
environment기상 상황, 전자 환경, GPS 신호 강도 등 환경 변수.
mission_weightMission Weight Model에서 계산된 도메인별 가중치 벡터. 모든 weight의 합은 100이다.

Mission Context Flow

Mission Context는 임무 계획 시스템과 연동하여 생성되고 업데이트된다. Mission Context Flow의 단계는 다음과 같다:

  1. Mission Plan Retrieval: 비행 계획과 임무 목표를 읽어 mission_type, mission_goal, critical_asset을 설정한다.
  2. Phase Detection: 현재 UAV의 위치, 시간, 연료 상태를 기반으로 mission_phase를 결정한다.
  3. Priority Assignment: 임무 목표의 중요도와 critical_asset의 중요도에 따라 mission_priority를 설정한다.
  4. Constraint & Environment Loading: No-Fly Zone, 시간 제한, 기상 정보를 수집하여 operational_constraint와 environment를 설정한다.
  5. Mission Weight Calculation: Mission Weight Model에서 mission_type과 mission_priority를 입력으로 받아 각 Capability의 weight를 계산한다. 예를 들어 Recon 임무에서는 Communication Trust와 Mission Trust weight가 높고, Strike 임무에서는 Command Trust와 Identity Trust weight가 높다.

Mission Impact Input

Mission Impact Model은 다음 입력을 사용한다:

  • Trust Object: Trust Layer에서 도메인별로 생성된 trust_score와 confidence.
  • Mission Context: mission_type, mission_phase, mission_priority, mission_weight, operational_constraint, environment 등.
  • Confidence: Trust Layer의 confidence 값. 임팩트 계산에 보수/낙관 계수로 사용된다.

Mission Impact Model

Mission Impact Model은 신뢰 점수와 mission_weight를 결합하여 임무 요소별 영향을 계산한다. 각 요소는 다음과 같이 정의된다:

  • Mission Availability: Communication Trust와 Session Trust의 weight가 적용된다. 신뢰 점수가 낮으면 C2 링크 끊김과 같은 가용성 감소가 발생한다.
  • Mission Integrity: Identity Trust와 Command Trust의 weight가 적용된다. 무인증 명령이나 권한 상승 공격이 감지되면 무결성이 감소한다.
  • Mission Safety: Mission Trust와 Command Trust의 weight가 적용된다. GPS 위변조나 위험 명령 삽입은 안전에 직접 영향을 미친다.
  • Mission Continuity: Session & Network Trust와 Mission Trust가 포함된다. PFCP Delete, Session Reset 등의 공격이 지속되면 임무 연속성이 떨어진다.
  • Recoverability: Recovery Feasibility Model에서 계산한 expected trust recovery와 mission recovery를 반영한다. 신뢰가 낮아도 복구 성공 확률이 높으면 recoverability는 상승한다.
  • Mission Risk: 위 요소들을 통합한 전반적 위험 점수이다. 위험 점수는 mission_weight와 trust_score를 곱한 값을 합산한 후 Confidence로 조정하여 계산된다.

Mission Impact Output

Mission Impact Layer는 다음 정보를 생성한다:

  • Mission Impact Object: mission_availability, mission_integrity, mission_safety, mission_continuity, recoverability, overall_mission_impact, mission_risk 등 필드를 포함한다.
  • Mission Summary: mission_impact 객체의 결과를 설명하는 간단한 메시지(예: "Session trust is low due to PFCP delete attempts; mission continuity at risk").

Mission Interface

Mission Impact Layer는 Policy & Recovery Layer에 다음 정보를 전달한다:

  • Mission Impact Object
  • Mission Context Object
  • Trust Vector & Confidence
  • Mission Risk Indicator (overall risk score)

Mission Failure Handling

Mission Context & Mission Impact Layer는 다음 상황에 대응한다:

  • Missing Mission Context: Mission Context가 없을 때 기본 값(평균 weight, low priority)을 사용하고, Policy Layer에 경고를 전달한다.
  • Invalid Mission Weight: mission_weight 합이 100이 되지 않으면 normalize하여 재조정하고 알림을 생성한다.
  • Extreme Mission Risk: mission_risk가 임계치 이상이면 Policy Layer에 긴급 경보를 발생시켜 즉각적인 판단을 준비한다.

Design Constraints

Mission Context & Mission Impact 설계의 제약 조건:

  • Mission Weight Model은 mission_type과 mission_priority에 따라 사전에 정의되어 있으며, 임무 실행 중 동적으로 변경할 수 없다.
  • Mission Impact Model은 신뢰 점수와 mission_weight를 곱하여 임팩트를 계산하므로, 신뢰와 가중치의 상관관계를 명확히 유지해야 한다.
  • Mission Risk 계산에는 confidence가 반드시 포함되어야 하며, 낮은 confidence는 위험을 보수적으로 증가시키는 방향으로 반영한다.
  • 임무 안전을 위해 Mission Context Object는 실시간으로 업데이트되어야 하지만, Mission Impact 평가는 Observation Window 단위로 수행한다.

Summary

Mission Context & Mission Impact Architecture는 Trust Layer에서 계산된 신뢰 점수를 임무 맥락에 따라 해석하고, 임무의 각 요소에 미치는 영향을 정량화한다. Mission Context Object가 mission_type, mission_phase, mission_weight 등을 제공하며, Mission Impact Model은 availability, integrity, safety, continuity, recoverability, risk를 계산한다. 결과는 Policy & Recovery Layer로 전달되어 정책과 복구 전략을 선택하는 데 사용된다.

8. Policy & Recovery Architecture

Purpose

Policy & Recovery Architecture의 목적은 Mission Impact Layer가 제공한 임무 위험 정보를 바탕으로 적용할 정책과 회복 전략을 선택하는 것이다. 이 계층은 정의된 Policy Rule Object와 Recovery Object를 사용하여 임무 위험을 최소화하고, 임무를 안전하게 지속하거나 재구성하거나 중지하는 데 필요한 조치를 결정한다.

Policy Overview

Policy는 미리 정의된 규칙들의 집합으로, 특정 조건이 만족될 때 취할 행동을 지정한다. Policy Rule Object는 rule_id, priority, condition, action, exception, reason 필드를 포함하며, condition은 Mission Impact Object와 Trust Vector를 기반으로 평가된다.

Policy Priority

Policy에는 우선순위가 부여되며, 여러 규칙이 동시에 조건을 만족하는 경우 priority가 높은 규칙이 선택된다. Priority 값은 정수이며, 높은 숫자가 더 높은 우선순위를 의미한다.

Policy Evaluation Flow

  1. Rule Matching: Mission Impact Object와 Mission Context를 기반으로 모든 정책 규칙의 condition을 평가한다.
  2. Rule Selection: 조건을 만족하는 규칙을 priority 순으로 정렬하여 가장 높은 규칙을 선택한다. 여러 규칙이 동일 priority를 가지면 예외(condition) 필드를 통해 충돌을 해결하거나 Operator Confirmation 레벨로 넘긴다.
  3. Action Selection: 선택된 규칙의 action을 수행할 준비를 한다. action에는 Continue, Continue with Monitoring, Mission Reconfiguration, Graceful Degradation, Operator Confirmation, Mission Abort 등이 있다.

Policy Conflict Resolution

여러 규칙이 동일한 priority를 가지고 동시에 조건을 만족할 경우, 다음 순서로 해결한다:

  1. 규칙의 specificity 비교: 조건이 더 구체적인 규칙을 우선한다.
  2. 규칙의 exception 필드 확인: 예외가 발생하는 규칙을 배제한다.
  3. 해결되지 않으면 Operator Confirmation 단계로 보내어 사람이 직접 판단하도록 한다.

Action Selection

Policy Layer가 선택할 수 있는 주요 행동과 그 조건은 다음과 같다:

ActionApplicable ConditionDescription
ContinueMission Risk이 낮고 모든 trust_score가 High 이상.임무를 정상적으로 지속한다.
Continue + MonitoringMission Risk이 Moderate이며 특정 도메인의 trust_score가 Moderate~High.임무를 계속하지만 특정 도메인을 집중 모니터링한다.
Mission ReconfigurationMission Risk이 Moderate~High이고 Recoverability가 높음.임무 경로나 작업을 재구성하여 위험을 완화한다.

Mission AbortMission Risk이 Very High 또는 trust_score가 Very Low.임무를 즉시 중단하여 자산과 안전을 보호한다.

Recovery Overview

Recovery Architecture는 정책에서 지정된 행동과 연계하여 복구 전략을 선택한다. Recovery Object는 recovery_id, recovery_type, execution_time, mission_delay, expected_trust_recovery, expected_mission_recovery, success_probability, resource_cost, recovery_risk, recovery_score 등 필드를 포함한다.

Recovery Candidates

Possible recovery actions include:

  • Session Reestablishment: PFCP/GTP 세션을 재설정하여 C2 연결을 복구한다.
  • Key Rotation: 세션 키 또는 인증 키를 갱신하여 identity trust를 회복한다.
  • Command Override: 임의 명령 삽입을 무효화하고 안전한 명령 세트를 강제한다.
  • Network Isolation: compromised UE를 격리하여 공격 확산을 방지한다.
  • Route Replanning: 임무 경로를 재계획하여 위험 지역을 회피한다.

Recovery Feasibility Model

Recovery Feasibility Model은 각 복구 후보의 실행 가능성을 평가하기 위해 다음 요소를 사용한다:

ElementDescription
execution_time복구 조치 수행에 걸리는 시간 (초).
mission_delay복구로 인해 임무가 지연되는 시간 (초).
expected_trust_recovery복구 후 trust_score가 얼마나 회복될 것으로 예상되는지 (0–100).
expected_mission_recoveryMission Impact 개선 정도. 예: mission_availability +20%.
success_probability복구 성공 확률 (0–1).
resource_cost사용되는 연료, 대역폭, 인력 등 자원의 소모 정도.
recovery_risk복구 과정에서 발생할 수 있는 새로운 위험. 예: 재설정 중 서비스 일시 중단.
recovery_score위 요소들을 결합하여 계산한 최종 점수. 높은 점수일수록 우선 적용된다.

Recovery Score는 다음과 같이 계산한다: recovery_score = (expected_trust_recovery × weight_trust + expected_mission_recovery × weight_mission) × success_probability − (recovery_risk + resource_cost + mission_delay). weight_trust와 weight_mission은 Mission Weight Model에서 정의된다.

Recovery Priority & Output

Recovery Candidates는 recovery_score를 기준으로 우선순위가 정해진다. 가장 높은 점수를 받은 후보가 선택되며, 선택된 복구는 Recovery Object와 함께 Mission Decision Layer로 전달된다.

Recovery Interface

Policy & Recovery Layer는 Mission Decision Layer에 다음 정보를 전달한다:

  • Selected Policy Action
  • Selected Recovery Object (회복 전략)
  • Priority List (정렬된 복구 후보 목록)
  • Reason (선택 배경 및 기대 효과)

Failure Handling

Policy & Recovery Layer에서는 다음과 같은 실패 처리를 정의한다:

  • No Rule Match: 어떤 규칙도 조건을 만족하지 않으면 default policy (Continue + Monitoring)를 적용하고 Operator Confirmation을 요청한다.
  • No Feasible Recovery: recovery_score가 모두 낮으면 mission_delay와 mission_risk를 평가하여 Mission Decision Layer에 Graceful Degradation 또는 Mission Abort를 권고한다.
  • Evaluation Timeout: 정책 평가나 복구 평가가 time limit 내에 끝나지 않으면 낮은 risk 행위를 택하고 Operator Confirmation을 호출한다.

Design Constraints

Policy & Recovery Architecture 설계 시 고려사항:

  • Policy Rule Object와 Recovery Object는 Core Architecture Model에서 정의한 필드를 그대로 사용해야 한다.
  • Policy Evaluation은 deterministic 해야 하며, 동일한 입력에 대해 항상 동일한 결과를 도출해야 한다.
  • Recovery Feasibility Model은 테스트베드에서 실측한 실행 시간과 성공률을 기반으로 보정되어야 한다.
  • 임무 우선순위가 높은 경우 mission_delay에 대한 penalty가 크므로 recovery_score 계산에서 반영되어야 한다.

Summary

Policy & Recovery Architecture는 Mission Impact를 해석하고 적절한 정책과 복구 전략을 선택하는 역할을 담당한다. Policy Evaluation Flow는 Rule Matching → Rule Selection → Action Selection의 단계를 통해 가장 적절한 행동을 결정하며, Recovery Feasibility Model은 회복 전략의 실행 가능성을 정량화한다. 결과는 Mission Decision Layer에 전달되어 최종 의사결정의 근거가 된다.

    - Determine action (Continue, Reconfigure, etc.)
    |

    - Generate recovery candidates
    - Compute recovery_score for each

9. Mission Decision Architecture

Purpose

Mission Decision Architecture의 목적은 Trust Layer, Mission Context & Mission Impact Layer, Policy Layer, Recovery Layer에서 제공된 정보를 종합하여 최종 임무 결정을 내리는 것이다. 이 계층은 각 데이터 객체를 기반으로 Mission Decision Object를 생성하고, 임무 지속, 재구성, 축소, 중단 등의 행동을 결정한다.

Decision Input Objects

Mission Decision Layer는 다음 객체를 입력으로 사용한다:

  • Trust Vector와 Trust Summary
  • Mission Context Object
  • Mission Impact Object
  • Selected Policy Action
  • Selected Recovery Object
  • Confidence (전반적인 confidence 값)

Decision Processing Flow

Decision Layer는 다음 단계로 진행한다:

  1. Compile Decision Context: Trust Vector, Mission Impact, Policy Action, Recovery Plan, Mission Context, Confidence를 하나의 결정 컨텍스트로 통합한다.
  2. Evaluate Decision Criteria: mission_risk, trust_scores, recoverability, policy_action, mission_priority 등을 비교한다.
  3. Select Decision Level: 아래 정의된 Mission Decision Levels 중 하나를 선택한다.
  4. Create Decision Object: 선택된 decision, decision_reason, supporting_evidence, supporting_trust, supporting_policy, recovery_summary, decision_confidence, timestamp 등을 기록한다.
  5. Generate Decision Trace: Decision Trace Model을 사용하여 Evidence→Trust→Mission Context→Mission Impact→Policy→Recovery→Decision의 흐름을 기록한다.

Mission Decision Levels

Mission Decision Layer는 다음 여섯 가지 수준 중 하나를 선택한다. 각 수준의 적용 조건은 아래와 같다:

Decision LevelApplicable ConditionsDescription
Continuemission_risk ≤ Low (예: mission_risk < 0.3), 모든 trust_score ≥ 70, Recoverability 무관.임무를 정상적으로 지속한다. No recovery needed.
Continue + Monitoringmission_risk ≤ Moderate (예: 0.3 ≤ mission_risk < 0.5), 최소 하나의 trust_score가 Moderate 구간(50–69)이고 recoverability가 높음.임무를 계속하지만 위험 도메인을 집중 모니터링한다.
Mission Reconfigurationmission_risk ≤ High (예: 0.5 ≤ mission_risk < 0.7), 특정 도메인의 trust_score가 Low(30–49)이고 recovery_score ≥ threshold.임무 경로나 작업을 재구성하여 위험을 감소시킨다.
Graceful Degradationmission_risk ≥ High (예: 0.7 ≤ mission_risk < 0.8), 여러 도메인의 trust_score가 Low이며 recoverability가 중간.비핵심 작업을 중단하고 필수 기능만 유지한다.
Operator Confirmationmission_risk ≥ High, 정보가 불충분하거나 policy/rules가 충돌할 때.결정을 인간 운영자에게 위임하여 추가 지시를 받는다.
Mission Abortmission_risk ≥ Very High (예: mission_risk ≥ 0.8), 여러 도메인의 trust_score가 Very Low(0–29) 또는 no feasible recovery.임무를 즉시 중단하여 플랫폼과 안전을 보호한다.

Decision Output

Decision Layer는 다음 결과를 생성한다:

  • Decision Object: decision level, decision_reason, supporting_evidence, supporting_trust, supporting_policy, recovery_summary, decision_confidence, timestamp를 포함한다.
  • Decision Trace: Evidence→Trust→Mission Context→Mission Impact→Policy→Recovery→Decision 전체 흐름을 기록한 데이터 구조. 이는 사건 분석 및 감사에 사용된다.

Decision Interface

Mission Decision Layer는 Mission Control 또는 Operator Interface에 다음을 전달한다:

  • Decision Object
  • Decision Trace
  • Recommended Actions (if any)

Failure Handling

Decision Layer 실패 처리는 다음과 같다:

  • Incomplete Data: Trust Vector, Mission Impact, Policy 또는 Recovery 정보가 없으면 Operator Confirmation을 요청한다.
  • Conflict between Policy and Recovery: 두 계층의 행동이 충돌하면 mission_priority와 mission_risk를 기반으로 판단하거나 Operator Confirmation으로 넘긴다.
  • Decision Trace Error: Decision Trace 생성에 실패하면 최소한 Decision Object와 관련 주요 요소를 기록하고 경고를 남긴다.

Design Constraints

Mission Decision Architecture 설계 시 제약 조건:

  • 모든 결정은 deterministic해야 하며, 동일한 입력에 대해 동일한 결과를 보장한다.
  • 결정 로직은 확률적 요소를 포함하지 않으며, 확률은 confidence와 recovery_score를 통해 반영한다.
  • Mission Decision Levels의 조건은 Mission Weight와 Mission Impact Model에 의해 정규화된 값에 기반한다.
  • Operator Confirmation 단계에서는 사람의 판단이 개입되므로 로그와 이유를 명확히 기록해야 한다.

Summary

Mission Decision Architecture는 임무의 최종 행동을 결정하는 핵심 계층이다. Trust, Mission Context, Mission Impact, Policy, Recovery, Confidence를 종합하여 decision_context를 구성하고, Mission Decision Levels에 따라 Continue, Reconfigure, Degradation, Operator Confirmation, Abort 중 하나를 선택한다. 결정 결과와 이유는 Decision Object와 Decision Trace로 기록되어 Mission Control에 전달된다.

Mission Decision Flow Diagram

Trust Vector, Mission Context, Mission Impact, Policy Action, Recovery Plan, Confidence
     |
Decision Context Builder
     |
Decision Criteria Evaluation
     |
Decision Level Selection (Continue, Monitoring, Reconfigure, Degradation, Operator, Abort)
     |
Decision Object & Decision Trace
     |
-> Mission Control / Operator Interface

10. Attack Mapping & End‑to‑End Architecture Validation

Purpose

이 장의 목적은 12개의 공격 시나리오가 설계된 Mission‑Centric Defense Architecture 내에서 어떻게 처리되는지 자세히 설명하고, 전체 파이프라인의 유효성을 검증하는 것이다. Attack Mapping은 공격을 Capability, Evidence, Trust, Mission Impact, Policy, Recovery, Decision 단계에 매핑하고, End‑to‑End Validation은 아키텍처가 각 공격을 적절히 탐지하고 대응하는지 논리적으로 검증한다.

Attack Mapping Philosophy

Attack Mapping은 개별 공격을 별도의 탐지기로 처리하지 않고, 공통 Security Failure와 Capability를 기반으로 통합적으로 대응한다는 설계 철학을 반영한다. 공격을 분류하여 각 Capability가 감지해야 할 메트릭을 식별하고, 이후 Evidence → Trust → Mission Impact → Policy → Recovery → Decision의 연속적 흐름으로 처리한다.

Attack Classification

12개의 공격 시나리오를 다음과 같이 분류한다:

  • Transmission Layer Attack: PFCP Session Delete, GTP teardown 시도로 세션을 끊는 공격.
  • Identity & Access Attack: web API 무인증 호출, MongoDB 접근, NAS null 암호 설정 등 인증·권한 부여 실패를 노리는 공격.
  • Session & Network Attack: UE 격리 우회, GTP 브리징, NAS 암호 우선순위 오류, PFCP Add/Modify 메시지 위조.
  • Command Attack: MAVLink Replay, Unauthorized Command Injection, Command Format Abuse 등 명령 수준 공격.
  • Mission Attack: GPS Spoofing, Mission Plan Tampering, Environment Sensor Manipulation 등 임무 컨텍스트에 직접 영향을 주는 공격.

Capability Mapping

각 공격은 하나 이상의 Capability에 할당된다. 예를 들어 PFCP Session Delete는 Session & Network Trust Capability에서 탐지되고, web API Injection은 Identity & Access Trust Capability에서 처리된다. MAVLink Replay는 Command Trust Capability, GPS Spoofing은 Mission Trust Capability에 대응된다.

Trust Mapping

Evidence가 입력되면 각 도메인의 Trust Layer는 해당 증거를 사용하여 신뢰 점수를 감소시킨다. 예를 들어 PFCP Delete 시도가 여러 번 감지되면 Session Trust score가 낮아지고, Mission Impact에서 mission_continuity가 감소한다. 마찬가지로 GPS Spoofing 증거는 Mission Trust를 낮춰 mission_safety와 mission_integrity에 영향을 준다.

Mission Impact Mapping

Trust Score가 낮아질수록 Mission Impact Model은 mission_availability, mission_integrity 등 요소를 감소시키고 mission_risk를 증가시킨다. 예를 들어 Session Trust가 Very Low이면 mission_continuity가 크게 감소하여 Mission Risk가 High 이상으로 상승한다. Identity Trust가 낮으면 mission_integrity가 감소하고 Critical Asset 보호가 어려워진다.

Policy Mapping

Mission Impact 값에 따라 Policy Layer는 적절한 규칙을 선택한다. 예를 들어 PFCP Session Delete 공격에서 mission_risk가 Moderate이면 Continue + Monitoring 정책을 적용하고, 매우 낮은 Session Trust가 반복되면 Mission Reconfiguration이나 Graceful Degradation을 선택한다. GPS Spoofing으로 mission_safety가 Low가 되면 Mission Abort가 고려된다.

Recovery Mapping

Policy에서 선택한 행동과 함께 Recovery Layer는 적절한 복구를 선택한다. PFCP Delete의 경우 Session Reestablishment가 주요 복구이며, web API 공격에는 Key Rotation과 Access Control 강화가 포함된다. MAVLink Replay에 대해서는 Command Override와 시퀀스 번호 재동기화가 적용된다.

Mission Decision Mapping

정책과 복구를 거친 후 Mission Decision Layer는 mission_risk, trust_scores, recoverability를 평가하여 Decision Level을 결정한다. 예를 들어 PFCP Session Delete 반복이 감지되어 mission_risk가 High로 상승하면 Mission Reconfiguration 또는 Graceful Degradation이 선택되고, GPS Spoofing이 지속되면 Mission Abort로 이어질 수 있다.

Architecture Validation

Architecture Validation은 각 공격이 위와 같은 경로를 통해 적절히 탐지되고 대응되는지 논리적으로 검증한다. 예를 들어 PFCP Session Delete는 Session & Network Capability에서 PFCP_Delete_Attempt 메트릭으로 탐지되며, Threshold Policy가 Warning 이상일 때 Evidence를 생성하고 Incident로 그룹화한다. Trust Layer는 Session Trust를 낮추고 Mission Impact에서 mission_continuity를 감소시킨다. Policy Layer는 Continue + Monitoring 또는 Mission Reconfiguration을 선택하고, Recovery Layer는 Session Reestablishment를 제안한다. Mission Decision Layer는 mission_risk와 recoverability를 평가하여 Continue + Monitoring 또는 Reconfiguration을 결정한다. 이와 같이 모든 공격은 Capability→Evidence→Trust→Mission Impact→Policy→Recovery→Decision의 경로를 따라 처리되며, 임무 위험과 신뢰를 일관되게 평가한다.

Summary

Attack Mapping & End‑to‑End Architecture Validation Chapter는 12개의 공격 시나리오를 설계된 아키텍처의 각 계층에 매핑하고, 공격 발생부터 Mission Decision에 이르는 전체 데이터 흐름을 설명한다. Threat Classification, Capability Mapping, Evidence Mapping, Trust Mapping, Mission Impact Mapping, Policy Mapping, Recovery Mapping, Decision Mapping을 통해 각 공격이 어떻게 처리되는지 보여주며, Attack Mapping Table과 End‑to‑End Flow 다이어그램을 통해 아키텍처의 일관성과 완전성을 검증한다.
